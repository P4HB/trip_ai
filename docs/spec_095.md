# SPEC-095: 제출 Spec 후반부에 전체 서비스 구현 계획 추가

- 상태: Superseded
- 작성일: 2026-10-02
- 최종 수정일: 2026-10-02
- 관련 이슈: 기존 제출 본문을 보존하고 가을볕 예시와 같은 구현 계획을 뒤에 추가하라는 사용자 요청
- 관련 문서: [제출 Spec](../kaist_app/제출용/01_Trip_AI_1단계_Spec.md), [아키텍처](architecture.md), [데이터 계약](data_contracts.md), [CCU-MMR](ccu_mmr_algorithm_draft.md), [평가](evaluation.md), [개인정보](safety_privacy.md)
- 관련 코드: 제품 코드 변경 없음
- 선행 SPEC: SPEC-094, SPEC-019, SPEC-083, SPEC-084
- 대체 SPEC: [SPEC-096](spec_096.md). 사용자의 후반부 간략화 요청에 따라 최종 구현 계획은 §9~17로 개정했다. 아래 구현·검증 결과는 최초 추가본의 기록이다.

## 배경

제출 Spec §1~8은 사업 및 평가 항목 중심의 기획이다. 사용자는 이 본문을 그대로 유지하면서 가을볕 팀의 기술 명세서 형식을 참고한 구현 계획을 덧붙이도록 요청했다. 제주 MVP에 한정하지 않고 여행 추천·일정·숙박 및 렌터카 예약과 기업·기관 공급을 포함한 목표 서비스를 설계한다.

## 목표

- 기존 파일의 모든 바이트를 접두부로 보존하고 §9 이후에 기술 구현 계획을 추가한다.
- 기술 스택·아키텍처·화면·API·알고리즘·데이터·예약·결제·디자인·인증·운영·개발 순서를 구체화한다.
- 기존 REQ/AC/NFR/BP/화면 ID와 구현 항목을 연결하고, 국가·언어·통화·시간대·다중 정보 및 예약 공급자를 수용한다.

## 비목표

- 기존 §1~8 및 도면·PDF 변경
- 제품 코드 구현·배포, 기존 MVP의 운영 설정 변경
- 특정 지도·결제·예약 공급자와의 계약, 요율·개발 일정·운영 실적 확정

## 요구사항

- REQ-001: 기존 본문을 변경하지 않고 후반부만 추가한다.
- REQ-002: 가을볕 기술 명세서의 기술 스택, 아키텍처, Frontend, Backend/API, Database, Design System, 결제, 인증, 비기능, 결정 항목에 대응하는 구현 계획을 작성한다.
- REQ-003: CCU-MMR의 필수 제약·취향·다양성 분리, 연속 취향 프로필, 상관 특성 가중치, LLM 일정 제안과 서버 검증, 출처·버전 추적을 기존 설계에서 계승한다.
- REQ-004: 지역별 기능 지원, 국가·지역 식별, 언어·시간대·통화, 다중 공급자 ID와 데이터 품질을 공통 계약으로 설계한다. 제주·자동차·특정 데이터 건수를 전체 서비스 한도로 사용하지 않는다.
- REQ-005: 예약·결제·취소·환불·정산의 상태를 분리하고 사용자 동의, 재확인, 멱등 처리, 웹훅 인증·순서 역전·대사를 계획한다.
- REQ-006: 선행 작업과 단계별 산출물·완료 조건·시나리오를 정의하고, 기준안과 외부 계약 의존 결정을 구분한다.

## 입력과 출력

- 입력: 제출 Spec v1.5, 가을볕 예시 Markdown, 관련 프로젝트 SPEC 및 기준 문서, 선택 기술의 공식 문서
- 출력: 동일 제출 파일의 §9~20 구현 계획, 색인·안내·아키텍처의 참조 링크
- 입력 원문 백업과 SHA-256·길이는 `kaist_app/_work/implementation_append_20261002/`에 저장한다.

## 설계

- 전체를 목표 구현 계획으로 표시한다. 기술 기준안은 React Native·TypeScript 앱, React 웹, Python·FastAPI 백엔드, PostgreSQL·PostGIS와 비동기 작업 처리다. 특정 공급자·배포 리전·거래 책임과 요율은 상세 설계 및 계약에서 정한다.
- 모듈 단위 백엔드와 작업 실행기를 분리하고 공개 데이터, 개인 여행 데이터, 예약·정산 기록의 책임을 구분한다.
- 기존 요구사항 ID를 다시 정의하지 않고 화면·모듈·API·개발 단계·검증 항목에서 참조한다.
- 장소 적합도와 실제 날짜를 사용하는 일정 가능성을 분리한다. 상품 가격·가용성과 예약 완료는 공급자 응답으로 확인한다.
- 실행 중인 시스템의 기준 문서는 덮어쓰지 않고 목표 구현 계획의 위치만 연결한다.

## 예외와 폴백

- 지역·교통수단·공급자 지원 부족은 지원 현황으로 반환하고 가능한 탐색·추천을 유지한다.
- 날짜 없는 요청은 일정 초안까지 허용하고 시간표·예약 확정에는 날짜를 요구한다.
- 외부 서비스 장애와 예약 상태 불명확을 구분해 재시도·조회·문의로 연결한다.

## 구현 결과

- 제출 Spec의 기존 47,220바이트를 그대로 보존하고 §9~20 구현 계획을 추가했다. 원본 SHA-256과 최종본 접두부가 일치한다.
- 기술 스택, 시스템 구성도, 화면·상태, API, 추천·일정, ERD·데이터 계약, 숙박·렌터카 예약·결제·정산, 디자인, 인증·개인정보, 비기능·운영, 개발 단계·시험을 작성했다.
- 기존 기능·비기능 요구사항과 화면·프로세스·승인 기준을 연결했다. 개발 단계는 7개, 통합 검증 시나리오는 15개이며 집계·보고 자동화의 P1 우선순위를 유지했다.
- 국가·언어·시간대·통화·이동수단·다중 공급자를 공통 계약으로 다루고, 필수 제약과 미확인 정보·예약 상태·결제 및 환불 상태를 분리했다.
- 제출 안내, 문서 색인, 아키텍처에서 구현 계획 위치를 연결했다. 기존 본문·제품 코드·도면·PDF는 변경하지 않았다.
