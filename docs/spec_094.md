# SPEC-094: 목표 서비스 중심의 1단계 기획과 여행 예약 연결

- 상태: Implemented
- 작성일: 2026-09-30
- 최종 수정일: 2026-09-30
- 관련 이슈: 사용자의 숙박·렌터카 예약 제안 및 현재 MVP와 독립적인 제출 기획 요청
- 관련 문서: [1단계 제출 Spec](../kaist_app/제출용/01_Trip_AI_1단계_Spec.md), [사업 기준](business_model_and_social_impact.md)
- 관련 코드: 제품 코드는 변경하지 않음. 도면 생성은 `kaist_app/_work/build_process.py`, PDF 생성은 `kaist_app/_work/render_process_pdf.py`
- 선행 SPEC: SPEC-091, SPEC-092, SPEC-093

## 배경

기존 제출 원고는 제주 베타의 구현 상태를 상품·시장 진입·기능 범위의 기준으로 삼았다. 사용자는 1단계 Spec이 목표 서비스와 사업구조를 정의해야 한다고 정정했고, 여행 추천 앱에서 숙박·렌터카 예약으로 바로 이어지는 서비스 가치를 추가하도록 요청했다. 기업용 추천 웹이라는 별도 상품 가정 대신 사용자가 제안한 여행 추천·예약 앱을 중심으로 기획한다.

## 목표

- 전 세계 여행시장을 대상으로 추천·일정 구성·숙박 및 렌터카 예약을 연결하는 목표 서비스를 설명한다.
- 문제·솔루션·상품·수익·성과·Actor·기능·도면을 같은 서비스 정의로 연결한다.
- 현재 구현 상태와 내부 검증 한계는 제출 본문에서 분리하고, L01~L03의 기획·사업전략 항목을 유지한다.

## 비목표

- 앱의 예약 기능 구현, 예약 공급사 선정·계약, 요율 확정, 실제 고객 접촉
- 기존 추천 알고리즘·배포·데이터 변경

## 요구사항

- REQ-001: 제출 본문은 목표 서비스의 기획안으로 작성하며 현재 MVP 지역·기술·개발 상태로 서비스 범위를 제한하지 않는다.
- REQ-002: PRD-01을 여행 추천·예약 앱으로 정의하고, 여행 추천→일정 구성→숙박·렌터카 예약을 문제·솔루션·상품·고객 가치에 연결한다.
- REQ-003: 여행자·예약 공급 파트너·기술 구매 고객을 구분하고, 예약 거래의 제휴 수수료와 B2B·B2G 공급 매출을 설명한다.
- REQ-004: 예약 기능을 핵심 범위에 포함하고 공급자 확인, 사용자 확정, 가격·재고 변경, 실패·취소 상태를 기능·화면·예외·데이터로 추적한다.
- REQ-005: 전 세계 TAM, 국내 트립빌더 비교, 당사 관점의 초기 고객 접촉·거래 기준 및 강의 반영을 유지한다.
- REQ-006: 연결된 도면·PDF·안내·검토·사업 기준을 동기화한다.

## 입력과 출력

- 입력: 사용자 사업 방향, 기존 제출 원고와 연결 문서·도면
- 출력: v1.5 Markdown 제출 원고, 편집 가능한 3장 draw.io와 같은 내용의 PDF, 관련 문서
- 데이터 마이그레이션과 실사용자 정보 처리는 없음

## 설계

- 결정: 목표 서비스는 여행 추천·예약 앱, 추천 API, 지역 관광 데이터·운영 패키지로 구성한다.
- 결정: 추천 이용과 여행상품 구매를 구분한다. 예약에 필요한 날짜·가격·이용조건을 확인하고 사용자가 확정하는 흐름을 핵심 서비스로 계획한다.
- 계획: 예약 파트너와 상품·가용성·예약 상태를 연계하고 확정 거래를 기준으로 제휴 수익을 관리한다. 이 문서 변경은 해당 기능의 구현 완료를 뜻하지 않는다.
- 미결정: 공급사, 앱 내 결제 또는 파트너 결제의 연동 방식, 예약 처리 책임·수수료율·정산 주기는 후속 상세 설계·계약에서 결정한다.
- 제출 원고에 현재 구현 목록을 복제하지 않는다. 전략 수단으로서의 MVP 개념은 L03 반영에 남긴다.
- L1은 전체 가치 교환, L2-A는 추천·일정·예약을 연결한 여행자 흐름, L2-B는 기업 도입·데이터 운영·계약 갱신 흐름으로 구성한다.

## 예외와 폴백

- 필수 입력 누락과 빈 추천은 기존 입력을 보존하고 사용자 수정으로 연결한다.
- 가격·가용성 변경은 갱신 정보로 재확인을 요청하고 자동 확정하지 않는다.
- 공급자 응답 지연·실패 시 예약 완료로 표시하지 않고 상태 확인·재시도를 제공한다. 취소도 공급자 결과를 확인해 표시한다.

## 승인 기준

- AC-001: 제출 원고에 현재 MVP의 구현·검증 목록이나 제주 한정 상품 정의가 없고, 추천·일정·예약이 핵심 서비스로 설명된다.
- AC-002: 상품·수익·고객·성과에 숙박·렌터카 예약과 여행 준비 편의가 연결되고 기존 승인된 시장·경쟁·고객 기준이 보존된다.
- AC-003: 예약의 요구사항·승인 기준·Actor·화면·예외·데이터·도면이 연결되며 8장 구성과 L01~L03 반영이 유지된다.
- AC-004: Markdown 링크·표·참조 ID, draw.io 연결선, PDF 3장의 한글·잘림·겹침을 확인한다.

## 구현 결과

- 제출 Spec을 v1.5로 갱신했다. 현재 제주 MVP의 구현 목록·기술 스택·근사 일정·예약 후순위 전제를 제거하고 목표 서비스와 사업계획으로 정리했다. L03의 MVP는 사업 검증 방법으로만 남겼다.
- PRD-01을 여행 추천·예약 앱으로 정의했다. 예약 과정의 단절을 원인 W4로 추가하고 해결 방식·앱 이용 예시·시장·고객·제휴 수수료·접근성·성과지표에 연결했다. 전 세계 TAM, 국내 트립빌더, 접촉·거래 중심의 초기 고객 선정 기준을 유지했다.
- 예약 파트너 SUP, 핵심 요구사항 REQ/AC-011·T11, BP-07, S07·S08, E06·E07을 추가하고 개인정보·신뢰성·거래 상태·정산 설계를 동기화했다.
- draw.io와 PDF를 같은 정의에서 3장·59개 연결선으로 갱신했다. L1은 추천·예약·정산과 기업·기관 공급, L2-A는 여행자 추천·일정·예약, L2-B는 고객 도입·데이터 운영·갱신이다.
- 안내·전략 보완·평가 대조·사업 기준·색인을 갱신했다. 이전 산출물은 `kaist_app/_work/before_target_service_v15/`에 보존했다.
- AC-001·002: 목표 범위, 문제→솔루션→상품→수익·성과의 의미 대조 통과. 구현 종속 문구 제거와 기존 승인 사항 유지 확인.
- AC-003: 8장 구성, 강의 반영, 기능·승인 기준 각 11개, 비기능 6개, 프로세스 7개, 여행자 화면 8개와 도면 참조 확인.
- AC-004: Markdown 6개 문서의 표 30개·로컬 링크 12개·인코딩·참조 ID 확인. draw.io 3장의 연결선 59개 참조 및 무관한 도형 내부 통과 0건. PDF 3장 한글 텍스트 추출·전체 페이지 렌더를 확인했고 글자 잘림·도형 위 겹침을 수정한 최종본을 검토했다.
