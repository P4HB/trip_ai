# CCU-MMR 장소 추천 알고리즘 초안

- 문서 상태: 설계 초안, 미구현
- 작성일: 2026-08-12
- 관련 SPEC: [SPEC-008](spec_008.md)
- 관련 기준 문서: [추천 알고리즘](recommendation_algorithm.md), [평가 전략](evaluation.md)

> 이 문서는 41개 장소·상황 라벨을 활용하는 차기 추천 알고리즘 후보를 처음 보는 사람도 이해할 수 있도록 정리한 설명서다. 현재 추천 엔진의 구현 완료나 운영 적용을 의미하지 않는다. 기존 `baseline-v0`와의 통합·대체 여부 및 모든 계수는 평가 후 SPEC에서 승인해야 한다.

## 1. 한 문장 정의

CCU-MMR은 **갈 수 없는 장소를 먼저 제외하고, 현재 여행에 중요한 라벨만 점수화하고, 근거가 약한 라벨은 보수적으로 보정한 뒤, 비슷한 장소의 반복을 줄여 추천 목록을 만드는 알고리즘**이다.

정식 명칭은 다음과 같다.

```text
CCU-MMR
= Constraint-First
+ Confidence-Shrunk Utility
+ Maximal Marginal Relevance
```

전체 흐름은 다음과 같다.

```text
전체 장소
→ 필수 조건 필터
→ 현재 요청에 필요한 feature 활성화
→ 라벨 신뢰도 보정
→ 취향·동행자·월·날씨 적합도 계산
→ 불확실성 및 조건부 위험 보정
→ MMR로 유사 장소 중복 완화
→ 실제 점수와 근거에 연결된 설명 생성
```

이 방식은 장소를 41차원 벡터로 놓고 단순 유사도만 계산하는 알고리즘이 아니다. **자격 판단, 요청별 효용 계산, 불확실성 처리, 목록 수준 다양화**를 순서대로 수행하는 다단계 랭커다.

## 2. 41개 라벨의 역할

### 2.1 장소 선호 라벨 24개

직접 점수에 사용하는 원자 라벨은 18개다.

| 그룹 | 라벨 |
|---|---|
| Theme 8 | `mountain`, `ocean`, `activity`, `culture_history`, `theme_park`, `cafe`, `traditional_market`, `festival` |
| Environment 2 | `indoor_ratio`, `weather_sensitivity` |
| Atomic Style 8 | `restfulness`, `physical_ease`, `visit_duration_flexibility`, `scenic_value`, `distinctiveness`, `local_embeddedness`, `landmark_significance`, `photo_value` |

파생 Style 6개는 직접 점수에 다시 넣지 않는다.

```text
healing_slow
scenic_immersion
discovery_explorer
local_immersion
iconic_highlight
photo_mood
```

파생 라벨은 원자 라벨로부터 만들어진 값이므로 함께 점수화하면 동일한 성격을 중복 반영할 수 있다. 따라서 다음 용도로만 사용한다.

- 사용자 표현을 원자 라벨 선호로 변환하는 프리셋
- 결과 설명을 사람이 이해하기 쉬운 표현으로 바꾸는 용도
- 탐색 UI의 요약 태그

### 2.2 상황 라벨 17개

상황 라벨은 현재 여행 요청에 해당하는 축만 활성화한다.

| 그룹 | 라벨 수 | 사용 방식 |
|---|---:|---|
| 동행 유형 | 5 | `solo`, `couple`, `friends`, `kids`, `parents` 중 현재 구성에 해당하는 축 |
| 월별 적합도 | 12 | 실제 여행 기간에 포함된 월만 일수 비중으로 결합 |

따라서 매 요청에서 41개 라벨 전체를 동일한 비중으로 사용하지 않는다. 예를 들어 “8월에 부모님과 바다 풍경을 보고 싶고 많이 걷는 곳은 피하고 싶다”는 요청에는 주로 다음 축이 활성화된다.

```text
ocean
scenic_value
physical_ease
parents
month_8
weather_sensitivity
```

## 3. 1단계: 갈 수 있는 장소만 남긴다

취향 점수를 계산하기 전에 장소가 여행 조건을 충족하는지 판정한다. 영업 여부, 여행 날짜, 연령 제한, 예약, 접근성, 안전 조건 등은 라벨 점수와 분리된 필수 제약이다.

장소 상태는 다음 세 범주로 구분한다.

| 상태 | 의미 |
|---|---|
| `eligible` | 모든 활성 필수 조건을 충족하여 추천 가능 |
| `conditional` | 중요한 정보가 없거나 예약·최신 확인이 필요한 조건부 후보 |
| `ineligible` | 하나 이상의 필수 조건을 위반하여 제외 |

필수 조건 위반은 높은 취향 점수로 상쇄하지 않는다. 예를 들어 휠체어 접근이 필수인데 접근할 수 없는 장소라면 경관이나 로컬성이 높아도 추천하지 않는다.

중요한 정보가 `unknown`일 때의 정책도 항목별로 구분한다.

- 안전·연령·필수 접근성: 제외하거나 별도 조건부 목록으로 분리
- 축제 개최일: 여행 날짜와 겹침이 확인될 때만 후보에 포함
- 영업 여부: 조건부 후보로 두고 최신 확인 요구
- 예약 필요 여부: 조건부 후보로 두고 경고 표시
- 일반적인 취향 라벨: 평균값을 이용한 신뢰도 수축 적용

## 4. 2단계: 사용자 선호를 효용 함수로 바꾼다

각 활성 라벨에 대한 선호는 다음 구조로 표현한다.

```text
p_k = (mode, weight, target, tolerance, threshold)
```

| mode | 의미 | 예시 |
|---|---|---|
| `benefit` | 라벨 값이 높을수록 선호 | 바다 느낌이 강한 곳 |
| `avoid` | 라벨 값이 낮을수록 선호 | 활동적인 곳을 피함 |
| `target` | 특정 값에 가까울수록 선호 | 실내와 야외가 반반인 곳 |
| `ignore` | 이번 요청에서는 계산하지 않음 | 카페 여부는 상관없음 |

대표적인 효용 함수는 다음과 같다.

```text
benefit: u_k(x) = x
avoid:   u_k(x) = 1 - x
target:  u_k(x) = exp(-(x - target)^2 / (2 × tolerance^2))
ignore:  계산에서 제외
```

초기 중요도는 `0, 1, 2, 4`처럼 희소하게 입력한다.

- 관심 없음: 0
- 조금 중요: 1
- 중요: 2
- 매우 중요: 4

“반드시”라는 요구는 매우 큰 가중치로 표현하지 않고 필수 또는 소프트 제약으로 승격한다. 활성 가중치는 합이 1이 되도록 정규화한다.

## 5. 3단계: 라벨의 근거 신뢰도를 반영한다

같은 라벨 값이라도 직접 조사로 확인된 값과 장소 유형만으로 추정한 값은 동일하게 취급하지 않는다.

장소 `i`의 라벨 `k`에 대한 신뢰도는 다음 요소를 결합한다.

```text
r_ik = confidence_ik^gamma
       × status_reliability_ik
       × evidence_reliability_ik
```

- `confidence`: 라벨 판정 자체의 확신도
- `status_reliability`: 사람 검수, AI 초안 등 상태에 따른 신뢰도
- `evidence_reliability`: 공식·공공·보조 출처 등 근거 품질
- `gamma`: 신뢰도를 얼마나 강하게 반영할지 조절하는 계수

정보가 약하다고 라벨 값을 0으로 만들지는 않는다. 원래 값과 같은 장소 유형의 기준값을 다음처럼 섞는다.

```text
adjusted_x_ik
  = r_ik × x_ik
  + (1 - r_ik) × category_baseline_g(i),k
```

예를 들어 원래 값이 `1.0`, 신뢰도가 `0.25`, 같은 장소 유형의 평균이 `0.6`이면 보정값은 `0.70`이다.

```text
0.25 × 1.0 + 0.75 × 0.6 = 0.70
```

이 수축 방식은 “정보가 적다”를 “나쁜 장소다”로 잘못 해석하지 않게 한다. 대신 근거가 약한 극단값을 중립적이거나 유형 평균적인 값 쪽으로 보수적으로 이동시킨다.

활성 축의 근거가 얼마나 확보되었는지는 별도 coverage로 기록한다.

```text
Q_i = sum(active_weight_k × r_ik) / sum(active_weight_k)
```

구조적으로 적용되지 않는 라벨은 coverage 분모에서도 제외한다.

## 6. 4단계: 개인 취향 적합도를 계산한다

신뢰도 보정이 끝난 활성 라벨만 가중 평균한다.

```text
P_i
  = sum(active_weight_k × u_k(adjusted_x_ik))
    / sum(active_weight_k)
```

예를 들어 사용자 선호가 다음과 같다고 가정한다.

```text
ocean                weight 4
physical_ease        weight 2
local_embeddedness   weight 2
photo_value          weight 1
```

어떤 장소의 보정값이 각각 `1.00`, `0.75`, `0.80`, `0.90`이면 취향 적합도는 약 `0.89`다.

```text
(4×1.00 + 2×0.75 + 2×0.80 + 1×0.90) / 9 = 0.89
```

이 값은 장소의 절대적인 품질 점수가 아니라 **현재 사용자의 현재 여행 요청에 대한 적합도**다.

## 7. 5단계: 동행자·월·날씨를 결합한다

### 7.1 동행자 적합도

동행 유형이 하나라면 해당 축을 사용한다. 여러 유형이 함께 활성화되면 평균과 가장 낮은 값을 결합한다.

```text
A_i(G)
  = (1 - eta) × weighted_mean(companion_scores)
  + eta × min(companion_scores)
```

초기값은 `eta=0.5`를 후보로 둔다. 아이나 고령자의 안전·필수 접근성은 동행 점수가 아니라 별도의 필수 제약이다.

### 7.2 월별 적합도

여행 기간이 여러 달에 걸치면 각 달에 속한 일수로 가중 평균한다.

```text
M_i(date_range)
  = sum(days_in_month_m × month_score_i,m)
    / sum(days_in_month_m)
```

축제는 일반 월 적합도로 판단하지 않는다. 개최일이 여행 기간과 겹치지 않으면 제외하고, 겹치면 확인된 개최 가능성을 사용한다.

### 7.3 날씨 적합도

현재 날씨의 불리한 정도를 `b(context)`라고 하면 다음처럼 계산한다.

```text
W_i(context)
  = 1 - b(context) × weather_sensitivity_i
```

운영 중단이나 안전 통제는 날씨 점수보다 먼저 필수 필터로 처리한다. `indoor_ratio`는 사용자의 실내·야외 선호에 사용하고, 날씨 감점에는 기본적으로 `weather_sensitivity`만 사용하여 중복 반영을 피한다.

## 8. 6단계: 기본 점수와 불확실성 위험을 계산한다

활성화된 블록만 정규화하여 결합한다.

```text
B_i
  = normalized_sum(
      W_P × P_i,
      W_A × A_i,
      W_M × M_i,
      W_W × W_i,
      optional W_L × L_i
    )
```

평가 전 초기 block weight 후보는 다음과 같다.

| 블록 | 초기값 |
|---|---:|
| 개인 취향 `W_P` | 0.70 |
| 동행자 `W_A` | 0.15 |
| 월 `W_M` | 0.10 |
| 날씨 `W_W` | 0.05 |

사용자가 최대 이동시간을 필수로 지정하면 이동시간은 필터다. 단순 선호라면 별도의 감쇠 점수를 사용할 수 있다.

```text
L_i = exp(-travel_time_i / tau_L)
```

최종 관련도는 불확실성과 낮은 coverage, 예약 확인 등의 소프트 위험을 반영한다.

```text
R_i
  = clip(
      B_i
      - lambda_U × uncertainty_i
      - lambda_Q × (1 - Q_i)
      - soft_penalty_i,
      0,
      1
    )
```

초기 후보값은 `lambda_U=0.10`, `lambda_Q=0.05`다. 다만 confidence shrinkage와 위험 감점을 동시에 쓰면 불확실성을 두 번 벌점 줄 수 있으므로 다음 세 실험을 비교해야 한다.

1. 신뢰도 수축만 적용
2. 신뢰도 수축과 작은 위험 감점 적용
3. 수축 없이 위험 감점만 적용

## 9. 여러 사용자가 함께 여행하는 경우

먼저 각 사용자 `u`에 대한 장소 점수 `R_iu`를 별도로 계산한다. 그룹의 필수 제약은 모든 구성원이 통과해야 한다.

```text
group_constraint_j(i) = min_u constraint_ju(i)
```

그룹 만족도도 평균과 최소값을 결합한다.

```text
G_i
  = (1 - rho) × weighted_mean_u(R_iu)
  + rho × min_u(R_iu)
```

초기 후보값은 `rho=0.35`다. 가족 여행에서는 최소 만족도의 비중을 높이고, 취향 차이를 일부 허용하는 친구 여행에서는 낮추는 방식을 실험할 수 있다.

## 10. 7단계: MMR로 목록의 중복을 줄인다

관련도만으로 상위 장소를 고르면 해수욕장, 카페 또는 오름처럼 비슷한 장소가 반복될 수 있다. MMR은 관련성과 이미 선택한 장소와의 차이를 동시에 고려한다.

먼저 관련도 상위 후보군을 만든다.

```text
candidate_pool = Top M by R_i
초기 후보: M=100
```

첫 장소는 관련도가 가장 높은 후보를 선택한다. 이후에는 다음 값을 최대화하는 장소를 반복 선택한다.

```text
MMR(i)
  = lambda_MMR × R_i
  - (1 - lambda_MMR) × max(similarity(i, selected_place))
```

초기 후보값은 `lambda_MMR=0.75`, 결과 수는 `N=10`이다.

- `lambda_MMR` 증가: 관련도 우선
- `lambda_MMR` 감소: 다양성 우선

장소 간 유사도는 18개 원자 라벨의 가중 Gower 또는 Manhattan 거리로 계산한다. 비교 가능한 값이 없는 축은 mask로 제외한다.

```text
feature_distance(i,j)
  = sum(v_k × mask_ijk × abs(x_ik - x_jk))
    / sum(v_k × mask_ijk)

feature_similarity(i,j)
  = 1 - feature_distance(i,j)
```

발견용 목록에서는 같은 장소 유형과 같은 권역 여부를 추가할 수 있다.

```text
similarity(i,j)
  = 0.7 × feature_similarity
  + 0.2 × same_type
  + 0.1 × same_region
```

지역별·유형별 최소 개수가 제품 요구사항이라면 MMR에 기대지 않고 명시적인 coverage 제약으로 구현한다.

MMR은 발견용 Top-N 추천의 다양화 방식이다. 실제 일정에서는 지리적 거리를 다양성 벌점으로 사용하지 않고, 이동시간과 경로 비용을 별도 일정 최적화 문제로 계산한다.

## 11. 8단계: 실제 계산 근거로 설명한다

추천 설명은 점수에 실제로 사용된 feature의 기여도에서 만든다.

```text
contribution_ik
  = effective_weight_k
    × (utility_ik - baseline_utility_k)
```

설명에는 다음을 포함한다.

- 기여도가 높고 근거 신뢰도가 충분한 긍정 이유 2~3개
- 동행자·월·날씨 중 중요한 상황 이유 1개
- 충족한 중요 필수 조건
- 예약, 영업, 접근성 등 확인이 필요한 경고
- 각 사실과 연결된 evidence ID

파생 Style을 설명에 쓰더라도 실제 원자 feature의 기여로 분해한다. LLM은 구조화된 trace를 자연어로 바꾸는 역할만 하며 새로운 장소 사실이나 추천 이유를 만들어서는 안 된다.

근거가 약하면 표현의 확신도도 낮춘다.

```text
높은 신뢰도: "바다 경관과 보행 편의가 높아 추천합니다."
낮은 신뢰도: "장소 유형상 부모님과 방문하기 비교적 적합할 것으로 추정되지만 동선을 확인하는 것이 좋습니다."
```

## 12. 처음 보는 사람을 위한 예시

사용자 요청이 다음과 같다고 가정한다.

> 8월에 부모님과 제주를 여행한다. 바다 풍경과 제주다운 장소를 좋아하고 많이 걷는 곳은 피하고 싶다. 비가 올 수도 있다.

알고리즘은 다음 순서로 처리한다.

1. 영업, 날짜, 필수 접근성, 안전 조건을 충족하지 못하는 장소를 제외한다.
2. `ocean`, `scenic_value`, `local_embeddedness`, `physical_ease`, `parents`, `month_8`, `weather_sensitivity`만 활성화한다.
3. 각 라벨의 출처와 검수 상태를 이용해 신뢰도가 낮은 극단값을 유형 평균 쪽으로 조정한다.
4. 바다와 보행 편의에 높은 가중치를 주어 취향 적합도를 계산한다.
5. 부모님 동행, 8월, 현재 날씨를 결합한다.
6. 정보가 부족하거나 예약 확인이 필요한 장소에 작은 위험 감점을 준다.
7. 상위 결과가 해수욕장만 반복되지 않도록 MMR로 오름·박물관 등 다른 유형도 고려한다.
8. 실제 점수 기여와 evidence ID를 이용해 추천 이유와 확인 사항을 설명한다.

## 13. 이 알고리즘이 보장하려는 원칙

1. **가능성이 적합성보다 먼저다.** 갈 수 없는 장소는 점수화하지 않는다.
2. **현재 요청에 필요한 라벨만 사용한다.** 무관한 축은 중립값이 아니라 계산 제외다.
3. **정보 부족을 낮은 품질로 해석하지 않는다.** 근거가 약하면 평균 쪽으로 수축한다.
4. **필수 조건과 선호를 분리한다.** 높은 선호 점수로 안전·접근성 위반을 상쇄하지 않는다.
5. **개별 장소 순위와 목록 다양성을 분리한다.** 관련도 계산 후 MMR로 목록을 구성한다.
6. **장소 추천과 일정 최적화를 분리한다.** 장소 적합도와 경로 효율을 같은 점수로 섞지 않는다.
7. **설명은 계산 trace에 충실해야 한다.** 사용하지 않은 라벨이나 확인되지 않은 사실을 이유로 만들지 않는다.

## 14. 평가 전 초기값과 미결정 사항

다음 값은 확정된 운영 파라미터가 아니라 실험을 시작하기 위한 seed다.

| 항목 | 초기 후보값 |
|---|---:|
| 취향/동행/월/날씨 block | `0.70 / 0.15 / 0.10 / 0.05` |
| 동행 유형 최소 만족도 `eta` | `0.50` |
| 사용자 그룹 최소 만족도 `rho` | `0.35` |
| 불확실성 감점 `lambda_U` | `0.10` |
| coverage 감점 `lambda_Q` | `0.05` |
| MMR 관련도 비중 `lambda_MMR` | `0.75` |
| MMR 후보군 `M` | `100` |
| 기본 결과 수 `N` | `10` |
| feature/type/region 유사도 비중 | `0.70 / 0.20 / 0.10` |
| 상관 feature 그룹 가중치 cap 후보 | `0.35` |

구현 전 또는 오프라인 평가에서 최소한 다음을 결정해야 한다.

- 장소 유형별 baseline을 어떻게 산출하고 버전 관리할지
- 라벨 confidence, 검수 상태, 출처 등급의 reliability 계수
- `gamma`와 위험 감점의 이중 반영 여부
- 사용자 표현을 원자 feature와 hard constraint로 변환하는 규칙
- 조건부 후보를 일반 결과와 어떻게 분리해 보여줄지
- 그룹 유형에 따른 `eta`, `rho` 정책
- MMR 강도와 지역·유형 coverage 정책
- 결과 설명 템플릿과 evidence trace 계약

## 15. 학습 기반 랭커로 전환하는 조건

초기에는 해석 가능한 규칙과 전문가 pairwise 평가로 가중치를 보정한다. 학습 기반 랭커로 전환할 때는 단순한 로그 건수 하나만 기준으로 삼지 않는다.

다음 조건을 함께 확인한다.

- 필수 제약 schema와 최신성 관리가 안정적임
- 유형·지역·상황별로 대표성 있는 노출 로그가 존재함
- 저장, 상세 보기, 방문, 예약 등 reward 정의가 명확함
- 시간 순서 holdout에서 현재 기준선보다 일관되게 개선됨
- constraint violation, 지역·유형 coverage가 악화되지 않음
- confidence calibration과 구간 추정이 허용 수준임
- shadow mode에서 충분히 검증됨

운영 계획을 위한 거친 시작점으로 `10^4` 수준의 노출과 `10^3` 수준의 의미 있는 positive action부터 FM 또는 LightFM 계열 실험을 검토할 수 있다. 이는 학술적 전환 임계값이 아니며 segment별 learning curve와 power analysis로 판단해야 한다.

## 16. 현재 문서 체계에서의 위치

- 이 문서는 41개 라벨을 활용하는 **차기 CCU-MMR 후보 설계**다.
- 현재 기준 설계는 [추천 알고리즘](recommendation_algorithm.md)의 `baseline-v0`이며 추천 기능 자체는 아직 미구현이다.
- 두 안의 입력 feature, confidence 처리, 가중치, MMR 유사도 정의가 다르므로 구현 전에 [SPEC-008](spec_008.md)에서 통합 또는 대체 결정을 승인해야 한다.
- 실제 구현 변경에는 데이터 계약, 오프라인 평가 시나리오, 회귀 검증과 버전 추적을 함께 반영해야 한다.
