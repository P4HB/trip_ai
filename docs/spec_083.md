## 배경

### 현재 코드·데이터에서 확인한 사실

| 영역 | 실제 구현 | 이번 작업과의 연결 |
|---|---|---|
| 장소 추천 | `ccu-mmr.js`의 `rank()`가 브라우저에서 선호 기반 순위·코스 variant를 생성 | 추천 결과와 원래 관련도 유지 |
| 일자 배정 | `buildSchedule()`이 `schedule.dayClusters[]` 생성. 자동차 15km·비자동차 5km 중심 반경, 하루 최대 6곳·대표 유형당 1곳 | 하루에 들어갈 장소 후보로 재사용 |
| 표시 순서 | 일자 `placeIds`는 필수 장소·anchor·추가 추천을 이어 붙인 순서 | 방문 순서나 도착시간으로 해석할 수 없음 |
| 화면 | `app.js`의 `runRecommendation()` → `renderRecommendationOutput()` → `renderSchedule()` | 추천 뒤 별도 비동기 동선 단계 추가 가능 |
| 지도 데이터 | 2,153곳, 그중 41축 추천 준비 1,663곳. 좌표와 대표 유형 포함 | ID 기반 서버용 최소 카탈로그 생성 필요 |
| 카카오 리뷰 | SQLite 4,817건. 추천 준비 장소 중 후기 보유 1,094곳, 본문 보유 1,061곳 | 방문 시간대·체류시간 분석에 재사용 가능하지만 전체 coverage가 아님 |
| 리뷰 시점 | manifest의 수집 시각 `2026-08-23T23:55:05.456101+09:00`, 당시 최대 5건 스냅샷 | 현재 운영시간이나 전체 방문자 의견으로 취급하지 않음 |
| 운영정보 | TourAPI 수집기는 `areaBasedList2` 기본정보를 수집. 지도 번들에는 정규화된 운영시간·휴무·최종 입장시간·체류시간 필드가 없음 | 별도 수집·정규화 필요 |
| 이동정보 | 실제 경로·교통수단별 소요시간 연동 없음. `transportMode`는 `car` 또는 `no_car` | 비자동차를 대중교통·도보·택시 중 하나로 추측하면 안 됨 |
| 서버 | 표준 라이브러리 Python 서비스가 평가 저장과 리뷰 조회 제공. LLM·동선 endpoint 없음 | 기존 배포 구조에서 모듈을 분리해 추가하는 안 |
| 배포 | Vercel 정적 UI가 기존 서버의 평가·리뷰 endpoint로 프록시. 서버 배포 스크립트의 Caddy 경로도 두 API만 명시 | 새 endpoint는 Vercel과 기존 서버 양쪽 경로 추가 필요 |

`result.items`의 Top-N과 `schedule.dayClusters[].places`는 동일 집합이 아니다. 동선 입력은 실제 일자 배정 결과에서 만들고, Top-N만 전달해 일자 장소를 누락하지 않는다.

### 사용자 확정 요구

- 선호에 따른 장소 추천 다음에 동선을 만든다.
- 방문 순서·시간표 작성은 LLM API 호출을 사용한다. 별도 수식 기반 최적화 알고리즘을 만들지 않는다.
- 교통편, 이동시간, 별도 수집한 영업시간, 리뷰에 나타난 낮·일몰·야간 방문 적합성을 고려한다.
- 점심·저녁 시간의 동선 근처에서 후속 식당 검색·추천을 할 수 있어야 한다.
- **동선 생성에는 실제 여행 날짜가 필수다. 날짜 없는 기간 선택에 대한 동선·가상 시간표는 제외한다.**

### 제안과 가정

- 1차는 기존 일자 배정을 유지하고 하루 안의 방문 순서·시간을 생성한다. 일자 간 재배정은 후속 범위로 제안한다.
- 기존 일자 배정의 필수 장소와 anchor를 보존한다. 시간상 넣을 수 없는 선택 장소는 사유와 함께 미배정으로 반환한다.
- 첫 외부 경로 연동은 자동차부터 검증하는 안을 권장하지만 지원 교통수단 범위는 아직 미확정이다.
- 공통 LLM 인터페이스를 리뷰 분석과 일정 생성이 함께 사용한다. 공급자·모델은 아직 정하지 않았다.
- SPEC-018의 수식 기반 일자 배정 초안은 선행 구현 조건이 아니며 이번 문서가 그 기능을 구현하거나 대체 완료한 것은 아니다.

## 목표

- 실제 날짜와 하루 활동 범위 안에서 순서·도착·출발·이동·체류·식사 시간을 표현한다.
- 확인한 운영 제약과 리뷰에서 추론한 선호 시간대를 분리해 LLM에 제공한다.
- 서버 검증을 통과한 시간표와 확인이 필요한 시간표를 구분한다.
- 식당 검색에 필요한 식사 시간대, 앞뒤 위치와 이동 구간을 제공한다.
- 기존 추천 점수, 유형 상한, 일자 지도 강조와 장소별 평가를 보존한다.

## 비목표

- 맛집 후보 수집·랭킹·실제 식당 삽입 구현. 이번 범위는 연결 계약까지다.
- 전역 최단 경로 보장, 수식 기반 최적화, 기존 추천 점수 변경, SPEC-018 구현.
- 날짜 없는 동선, 날짜·요일·일몰 시각 추측, 실시간 내비게이션·GPS 추적.
- 예약·결제, 실시간 날씨에 따른 자동 재계획, 항공·선박 예약 및 복합교통 시간표 최적화.
- 계획 작성 중 운영 배포, 전체 재수집, 유료 LLM·경로 API 실행.

## 요구사항 — 계획·미구현

- `REQ-8301`: 출발일·종료일이 있는 요청만 동선 생성에 진입한다. 기간 정수만 있는 요청과 날짜 미정 요청은 UI·서버 모두 차단하고 날짜 입력을 안내한다. 날짜 순서·허용 범위를 검증한다.
- `REQ-8302`: 기존 추천 결과에 별도 동선 결과를 연결한다. 원래 점수·variant·일자 후보·제외 조건·필수 장소·anchor·하루 유형 상한을 임의 변경하지 않는다. 시간표 입력과 추천 revision을 연결한다.
- `REQ-8303`: 장소별 운영시간·휴무·입장 마감·예외 운영일을 원문·출처·확인 시각과 함께 보관한다. 불명확·충돌·오래된 정보는 `unknown` 또는 `verification_required`로 처리하며 상시 개방으로 간주하지 않는다.
- `REQ-8304`: 리뷰에서 낮·일몰·야간 적합성과 체류시간 근거를 구조화하고 `review_id`를 연결한다. 리뷰 없음·본문 없음·상충을 처리한다. 리뷰 추론은 운영시간 사실을 덮어쓰지 않는다.
- `REQ-8305`: 실제 이동수단에 맞는 경로 제공자의 예상 이동시간을 사용한다. 출발지·도착지 방향, 조회 시점과 예상 출발 시각을 보존한다. LLM이 이동시간을 생성하거나 직선거리로 확정 이동시간을 대신하지 않는다.
- `REQ-8306`: 일자별 출발·종료 위치와 활동 가능 시간, 체류시간, 이동·대기·휴식 여유를 입력에 포함한다. 누락은 `needs_input` 또는 명시적인 추정 정책으로 처리하며 숙소·항공편을 임의 생성하지 않는다.
- `REQ-8307`: LLM은 허용된 장소 ID에서 방문 순서와 시간 배치를 제안하고, 시간대 선택 이유에 근거 ID를 붙인 구조화 결과를 반환한다. 모델·프롬프트·스키마·카탈로그·운영정보·리뷰·경로 버전을 추적한다.
- `REQ-8308`: 서버가 ID, 중복·누락, 시간 겹침, 이동·체류·식사 시간, 운영시간·입장 마감, 종료 시각을 독립 검증한다. 알려진 필수 제약 위반은 성공으로 반환하지 않으며 필수 장소를 조용히 삭제하지 않는다.
- `REQ-8309`: 점심·저녁의 허용 시간대·소요시간·앞뒤 장소/출발지/종료지·경로 참조·허용 우회시간을 반환한다. 식당 미선정 상태를 표시하고, 후속 식당 확정 시 이동시간과 이후 일정을 재검증해야 한다.
- `REQ-8310`: LLM·경로 호출 실패, 시간 초과, 잘못된 출력, 지원되지 않는 교통수단에서 기존 장소 추천은 유지한다. 수정 요청·재시도·병렬 호출에 상한을 두고 오래된 응답으로 새 결과를 덮어쓰지 않는다.
- `REQ-8311`: API 키는 서버에만 둔다. 리뷰는 비신뢰 데이터로 다루고 외부 LLM에 이름·평가 의견·MBTI 원문을 전송하지 않는다. 공개 장소 데이터 캐시와 사용자 일정 데이터를 분리한다.
- `REQ-8312`: 기존 추천·평가·리뷰 회귀와 동선 고정 시나리오를 검증한다. LLM 출력 자체의 완전한 결정성을 약속하지 않고 검증기·입력·출력·버전 기록으로 재현·비교한다.

## 입력과 출력 — 제안, 미구현

새 계약은 기존 `schedule` 객체와 분리한 `itinerary-request-v1` / `itinerary-result-v1`로 제안한다. endpoint 후보는 `POST /travel/api/itineraries`다.

### 요청

- `requestId`, `recommendationRevision`, `courseVariantId`, `catalogVersion`: 현재 추천과 요청을 연결하는 문자열.
- `travelWindow`: 필수 `{startDate, endDate}`; 유효한 `YYYY-MM-DD`. 날짜는 서버에서도 재검증한다.
- `timezone`: `Asia/Seoul`.
- `routeMode`: 구체적인 이동수단. 기존 랭커의 `car|no_car`와 구분하고 지원 여부를 검증한다.
- `days[]`: `dayIndex`, `date`, `placeIds`, `requiredPlaceIds`, `anchorPlaceId`, `startLocation`, `endLocation`, `startTime`, `endTime`.
- 위치: 우선 공개 장소 ID로 선택하고 서버 카탈로그의 `{lng, lat}`를 사용한다. 좌표 배열을 쓰면 `[경도, 위도]`. 사용자 정확 좌표 입력은 보관·고지 정책 확정 전 추가하지 않는다.
- 시간: 요청의 현지 시각은 `HH:mm`, 내부 비교는 날짜를 포함한 시각, 결과는 `+09:00`이 있는 ISO 8601. 자정 이후 운영은 다음 날로 정규화한다.
- `mealPreferences`: 점심·저녁 각각 허용 시작·종료 시각, 식사 분, 우회 허용 분. 구체 기본값은 미확정이며 UI에서 변경 가능하도록 제안한다.
- `visitPace` 또는 체류시간 override: optional. 빠른 마감에 맞추려고 LLM이 근거 없는 짧은 체류시간을 만들지 않도록 허용 범위를 제공한다.

브라우저는 원본 리뷰·영업정보·경로시간을 권위 있는 값으로 보내지 않는다. 서버가 ID로 카탈로그·sidecar를 조회하고 클라이언트의 장소 정보·유형·수치 변조를 검증한다. LLM에 전체 MBTI 프로필 대신 일정에 필요한 장소·기존 우선순위·명시적인 여행 속도만 전달한다.

### 장소 시간 정보

- `operatingInfo`: raw text, 주간 운영 구간, 날짜별 예외, 휴무, 입장 마감, `sourceRefs`, `checkedAt`, `status`.
- `visitInsights`: `preferredPeriods[]` (`daylight|sunset|night|any|unknown`), 선택적 체류시간 범위(분), 대기·보행 관련 근거, `evidenceReviewIds`, 상충/부족 상태, 모델·프롬프트 버전, 입력 해시.
- 체류시간은 출처 기반 관람시간 → 리뷰 근거 추정 → 버전된 유형별 기본값 순으로 사용한다는 안이다. 추정·기본값은 사실과 구분하고 값을 정책 파일로 관리한다.
- 일몰·일출은 실제 날짜·좌표에서 별도 계산/조회한다. LLM이 임의로 18시 같은 고정 시각을 지정하지 않는다. 계산 방법은 구현 전에 선정·검증한다.

### 응답

- `status`: `validated|verification_required|partially_scheduled|infeasible|needs_input|unavailable` 제안. `validated`도 입력 시점의 예상 일정이며 실제 이동 보장이 아니다.
- `days[].stops[]`: 장소 ID, 방문 순서, 도착·출발, 체류 분과 근거 종류, 운영정보 확인 상태, 시간대 선택 근거 ID.
- `days[].legs[]`: 출발·도착 위치 ID, 예상 출발·도착, 소요시간, 제공자·조회 시각·예측 기준, 경로 참조. 원천 초 단위를 유지하고 표시 분 변환 시 보수적으로 올림한다.
- `days[].mealSlots[]`: `slotId`, `lunch|dinner`, 허용 시간대와 배정 시간, 식사 소요시간, 앞뒤 위치, 관련 경로 참조, 우회 허용 분, `restaurantStatus=pending`.
- `unscheduledPlaces[]`: 입력 중 미배정된 모든 장소와 이유, 필수 여부. 시간표에 없어진 장소를 누락하지 않는다.
- `violations[]`, `unknowns[]`, `assumptions[]`, `provenance`: 검증 결과와 데이터 시점·LLM·프롬프트·설정 버전.
- 일정 상태 외에 `restaurantIntegrationStatus=pending`을 유지한다. 식당 선택 전에는 식당까지의 이동 검증이 완료된 것으로 표시하지 않는다.

## 설계 — 구현 순서 제안, 모두 미구현

### 1. 연결 계약과 날짜·이동 입력

`rank()`와 `buildSchedule()` 결과는 유지하고 `dayClusters`를 새 요청으로 변환하는 경계를 먼저 만든다. 실제 날짜, 이동수단, 출발·종료 위치/시간을 확인한 뒤 사용자가 동선 만들기를 실행한다. 기간만 선택했으면 실제 날짜 입력으로 유도하고 LLM을 호출하지 않는다.

추천 화면에 있던 날짜 미정/기간 선택을 전부 제거할지는 이번 동선 요구와 별개의 기존 UI 변경이다. 이 초안은 해당 선택만으로는 새 동선을 만들 수 없도록 하는 범위를 확정하며, 날짜 없는 기존 근사 군집을 시간표로 표시하거나 새 동선으로 승격하지 않는다.

완료 기준: 고정 응답으로 요청·응답과 로딩·오류·날짜 누락 상태를 검증할 수 있다.

### 2. 영업정보 수집과 서버 카탈로그

기존 TourAPI ID를 그대로 사용해 별도 상세정보 수집기를 만든다. TourAPI 소개정보를 우선 조사하고 누락은 공식 장소 출처로 보완할 수 있도록 수집 경계를 둔다. 현재 API의 유형별 필드와 실제 응답은 구현 초기에 표본으로 확인한다. 기존 웹 조사 문장이나 카카오 리뷰를 최신 영업시간으로 승격하지 않는다.

원문과 정규화 결과를 날짜별 sidecar·manifest로 저장하고, 서버용 최소 장소 카탈로그와 결합한다. 영업시간·주간 휴무·계절별 시간·입장 마감·자정 경계·공휴일 예외를 각각 표현한다. 설명이 모호하면 원문과 `unknown`을 보존한다. 수집은 재개 가능하게 만들고 실패·누락 coverage를 보고한다.

완료 기준: 대표 유형 표본에서 원문과 구조화 값이 연결되고, 파싱 실패·누락이 방문 가능으로 바뀌지 않는다.

### 3. 공통 LLM 인터페이스와 리뷰 분석

공급자 중립 `generate_structured(task, input, schema, timeout)` 형태의 얇은 인터페이스를 제안한다. 운영 키·모델은 서버 설정에서 주입하고 테스트에서는 가짜 응답을 사용한다. 기능은 구조화 출력, 응답 검증, 시간 제한, 제한된 재시도, 토큰/지연/오류 집계에 한정한다.

카카오 DB의 승인된 ID 연결과 작성자명이 제거된 리뷰를 읽어 장소별 시간대·체류시간을 미리 분석한다. 리뷰 입력 해시·모델·프롬프트 버전이 바뀐 장소만 재분석한다. 방문 시간대 결론마다 리뷰 ID를 검증하고, 관련 없는 리뷰·별점만 있는 리뷰·상충 리뷰는 `unknown`/상충 상태로 남긴다. 리뷰 속 명령문은 실행 지시로 사용하지 않는다.

완료 기준: 매 일정 요청에서 같은 리뷰를 반복 분석하지 않으며 근거 없는 시간대·체류시간을 사실로 저장하지 않는다.

### 4. 이동시간 제공자 연결

경로 제공자를 `route_provider` 뒤로 분리한다. 전체 1,663곳 조합을 계산하지 않고 해당 일자의 최대 6곳과 시작·종료 위치 사이에 필요한 **방향별** 이동시간을 조회한다. 서로 반대 방향의 시간이 같다고 가정하지 않는다.

초기 순서 결정용 시간 표와 최종 선택 경로를 구분한다. LLM이 시간표를 제안하면 실제 배정 출발 시각으로 선택 구간을 다시 조회/검증한다. 캐시 키에 이동수단·좌표·날짜/시간대·제공자 옵션을 넣는다. 미래 시각 예측을 지원하지 않으면 조회 시점 추정이라는 제한을 명시한다. 조회 횟수·재검증 횟수·총 deadline에 상한을 둔다.

완료 기준: 자동차/대중교통/도보를 섞지 않고, 경로 없음·제공자 실패를 0분이나 LLM 추정으로 바꾸지 않는다.

### 5. LLM 시간표 생성과 서버 검증

서버가 일자별 장소, 운영 구간, 리뷰 분석 요약, 체류시간, 이동시간, 시작/종료, 식사 조건을 조합한다. 첫 버전은 일자 단위 구조화 호출을 제안하며, 부분 성공을 보존하고 실패한 날만 제한적으로 다시 만들 수 있게 한다.

LLM은 이 입력 안에서 순서·시간·식사 구간을 제안한다. 서버가 날짜/ID/중복/미배정/유형 상한/운영시간/입장 마감/시간 겹침/이동·체류 하한/종료 시각을 검사한다. 알려진 위반은 오류 목록을 붙여 수정 호출 1회까지만 허용한다는 안이다. 그래도 위반하면 성공 일정으로 노출하지 않는다. 데이터가 없는 제약은 검증 통과가 아닌 확인 필요로 남긴다.

전체 결과에서 필수 장소 누락·위반이 있으면 해당 사유와 `infeasible`을 표시하고 다른 날짜의 유효 결과는 보존한다. 필수 제약 위반 없이 선택 장소만 빠지면 `partially_scheduled`로 표시한다. 오류가 없더라도 미확인 운영정보가 있으면 `verification_required`다. 복수 상태 원인은 `violations`·`unknowns`에 모두 남긴다.

완료 기준: 빠른 마감·일몰 선호·긴 이동·점심 시간 충돌 사례에서 사실 기반 결과 또는 정직한 미배정/실패 사유를 반환한다.

### 6. 시간표·지도 표시와 식당 연결 계약

`app.js`에 동선 전용 상태와 `itinerary.js` 클라이언트를 추가하는 안이다. 추천 목록을 먼저 표시하고 명시적 동선 생성으로 호출한다. UI는 순번, 도착/출발, 이동·체류시간, 점심·저녁 자리, 근거 요약과 확인 필요를 보여준다. 경로 도형은 제공자가 반환한 경로일 때만 실제 이동 경로로 표시한다.

중요한 기존 코드 경계: `renderRecommendationOutput()`은 평가 세션을 새로 만들므로 동선 응답을 그 함수로 다시 렌더링하지 않는다. 동선 전용 갱신에서 현재 평가와 이름·별칭·선택 장소를 보존한다. 추천 재실행·variant·날짜 변경은 동선을 무효화하고 요청을 중단하며 revision이 다른 늦은 응답을 무시한다.

식당 검색은 식사 slot의 시간대와 앞뒤 위치·경로를 입력으로 삼는다. 단순 위경도 중점 하나로 검색 위치를 확정하지 않는다. 식당 선택 후에는 A→식당→B 이동, 식당 영업·주문 마감, 체류시간을 다시 반영해야 한다는 후속 계약을 둔다. 첫/마지막 식사는 시작·종료 위치도 앞뒤 지점으로 사용할 수 있다. 식사 자리를 못 만들면 조용히 생략하지 않고 사유를 반환한다.

완료 기준: 기존 모바일/데스크톱 추천·지도 강조·평가 자동 저장을 유지하면서 식당이 아직 미선정인 날짜별 시간표를 표시한다.

### 7. 통합 검증과 배포 준비

고정 시나리오와 기존 회귀를 먼저 통과시킨 뒤 대표 제주 장소로 제한된 실제 API 평가를 한다. 서버의 새 모듈·설정·카탈로그를 Docker 이미지에 넣고 Caddy의 명시 경로와 Vercel의 동일 출처 프록시에 동선 endpoint를 추가한다. 기존 프록시의 Origin 처리를 그대로 넓히지 말고 새 경로에 맞춰 검증한다.

LLM 비용이 발생하는 공개 endpoint에는 요청 크기·일수·호출 빈도·동시 실행·토큰·총 비용 상한을 둔다. 운영 타임아웃을 초과하면 실패시키고 추천 결과를 보존한다. 초기에는 bounded synchronous 요청을 제안하며, 표본 지연시간이 프록시 제한에 맞지 않으면 job/poll 방식으로 SPEC을 먼저 변경한다.

완료 기준: 새 기능을 끈 상태에서도 기존 서비스가 동작하고 실패 시 동선 기능만 되돌릴 수 있다.

## 예외와 폴백

- 날짜 없음: 생성 차단, 날짜 요청. 임의 날짜·요일을 채우지 않는다.
- 출발/종료 또는 이동수단 불명: 필요한 입력을 반환하고 LLM 호출 전 중단한다.
- 기존 `schedule.status=infeasible`, 빈 일자: 원래 사유를 유지하고 시간표로 해결한 것처럼 표시하지 않는다.
- 리뷰 없음/근거 불충분: 시간대 `unknown`; 체류시간 기본값을 사용하면 추정으로 표시한다.
- 운영정보 불명·오래됨·충돌: `verification_required`; 높은 선호나 좋은 리뷰로 통과시키지 않는다.
- 경로 없음·교통수단 미지원: 해당 구간을 방문 가능한 이동으로 만들지 않는다. API 장애는 `unavailable`과 재시도 안내다.
- LLM 거절/형식 오류/존재하지 않는 ID/근거 위조: 검증 실패. 제한된 재시도 후 기존 추천을 유지한다.
- 입장 마감과 일몰 선호 충돌: 입장 마감 우선. 일몰 방문이 불가능하다는 근거를 보여준다.
- 선택 장소 과다: 선택 장소 미배정과 이유를 모두 표시한다. 필수 장소를 제거해 성공으로 만들지 않는다.
- 식당 미선정: 식사 시간·우회 여유만 확보한 상태임을 표시하고 식당 확정 뒤 재검증한다.

- 데이터 마이그레이션: 기존 지도 번들·카카오 리뷰 DB·사용자 평가 DB를 덮어쓰지 않고 신규 공개 장소 sidecar/카탈로그로 시작한다.
- 호환성 영향: 원래 `schedule`은 근사 일자 배정으로 유지하고 새 `itinerary`를 별도 보관한다. 동선 변경만으로 평가 세션을 초기화하지 않는다. 기존 자동 평가 payload에는 새 출발·종료 위치나 LLM 원문이 자동 포함되지 않도록 명시적인 필드 선택을 사용한다.
- 보안·개인정보: 공용 장소 ID·좌표, 날짜·활동 시간과 최소 일정 조건만 처리한다. 리뷰 본문은 공개 후기 분석에만 보내고 사용자 이름·의견·MBTI 원문은 보내지 않는다. 본문 안 개인정보는 외부 전송 전에 최소화한다.
- 저장 제안: 공개 장소 분석은 버전된 sidecar로 보관하고 원본 해시로 갱신/철회한다. 사용자 일정·장소 선택·원문 프롬프트는 초기 버전에서 서버에 영속 저장하지 않는다. 요청 처리 후 해제하고 클라이언트는 현재 탭 메모리에서 초기화/종료 시 삭제한다. 운영 로그에는 내용·좌표 대신 비식별 오류/지연/사용량만 남긴다. 외부 제공자의 보관 설정은 공급자 결정 후 고지에 반영한다.
- 기존 기준 문서와의 차이: 현재 리뷰는 표시 전용이지만 이번 계획은 시간대 추론에 사용한다. 구현 시 이 경계와 날짜·위치의 외부 전송 목적을 기준 문서/사용자 고지에 함께 반영해야 한다.

- `AC-8301` (`REQ-8301`): 실제 날짜 없음·기간만 선택·역순 날짜는 UI/서버에서 차단되고 외부 호출 횟수는 0이다.

- `AC-8306` (`REQ-8306`): 시작·종료, 체류·여유를 포함하고 출발/종료 정보가 없으면 생성하지 않는다. 추정 체류시간은 출처 기반 값과 구분된다.

## 테스트 계획

### 여기서 말하는 검증

1. **자동 조건 검사**: LLM 시간표가 입력으로 제공한 운영시간·이동시간·체류시간·필수 장소 조건을 지키는지 코드로 확인한다. 예를 들어 17시 마감, 관람 60분, 다음 장소까지 이동 30분인 가상 조건에서 `16:30~17:30 관람 → 17:40 다음 장소 도착`은 마감 위반과 이동시간 부족으로 검출해야 한다. 위반 목록을 LLM에 전달해 제한된 횟수 안에서 수정한다.
2. **예시 일정 품질 확인**: 실제 장소 20~30곳으로 만든 표본 일정에서 지나치게 짧은 체류, 불편한 식사 시각, 불필요하게 되돌아가는 순서를 살펴보고 초기 설정과 프롬프트를 조정한다. 사용자가 모든 장소를 직접 검수해야 한다는 요구는 아니다.

자동 검사는 주어진 데이터와 시간표의 일치 여부를 확인한다. 원천 영업정보·예상 이동시간 자체의 현실 정확도까지 보장하지 않는다. 첫 구현에서는 시간 겹침, 이동시간 확보, 영업시간 준수, 필수 장소 누락 검사를 우선 연결하고 아래 승인 기준을 단계적으로 완성한다.

평가 fixture에는 최소한 조기 마감, 야경과 입장시간 충돌, 일몰 날짜 차이, 월요일 휴무, 운영정보 없음, 자정 경계, 본문 없는 리뷰, 상충 리뷰, 방향별 이동시간 차이, 경로 없음, 식사 창과 필수 장소 충돌, 시작/종료 이동 누락, 첫날 늦은 도착·마지막 날 이른 출발, 오래된 응답을 포함한다. 기존 카드 순서로 만든 단순 순서 기준선과 비교하되 기존 카드가 실제 이동 최적화를 수행했다고 가정하지 않는다.

## 알려진 제한

- 현재 리뷰 본문이 없는 추천 준비 장소는 602곳이다. 리뷰를 더 수집하지 않으면 그 장소의 시간대 분석은 다른 근거나 `unknown`에 의존한다.
- 실제 영업정보 coverage·신선도는 아직 조사하지 않았다. TourAPI 소개정보 제공 여부와 모든 장소의 운영정보 완전성은 별개다.
- 기존 일자 배정을 유지하면 날짜를 바꿔야만 가능한 장소 조합을 자동 해결하지 못한다. 이를 LLM 순서 변경만으로 해결할 수 있다고 가정하지 않는다.
- 제공자 선택·키·호출 한도·비용·데이터 이용 조건, 운영 배포와 실제 외부 호출은 이번 계획에서 검증하지 않았다.
- LLM은 좋은 동선이나 전역 최적해를 보장하지 않는다. 검증기는 제공된 데이터로 확인 가능한 위반을 차단하며 현실의 미수집 제약까지 보장하지 못한다.
