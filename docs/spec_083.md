## 1차 검토 보완 — 2026-09-24 승인된 범위와 결정

사용자의 「보완 진행」 요청으로 아래 다섯 항목을 승인된 범위로 추가한다. 이 절은 이전 기본값·계약과 충돌할 때 우선한다. 실제 외부 API 평가·운영 배포는 이번 보완 완료와 구분한다.

- **배경/사실**: 오후 시작에도 두 식사를 강제하고, 모델 형식 오류도 `infeasible`로 분류했다. 하루 8지점의 방향별 56회 참고 조회는 7일에 392회로 기존 전체 280회 상한을 초과했다. 수정 입력에는 실제 출발시각의 경로 수치가 빠졌고 실제 품질 합격선이 없었다.
- **목표**: 부분 일자 지원, 생성 실패의 정직한 분류, 7일 생성의 호출 예산 정합성, 근거 있는 수정, 측정 가능한 실제 품질 gate.
- **비목표**: 일자 재배정·수식 최적화·식당 선정·공급자 변경·실제 API 실행·배포.
- `REQ-8313`: 일자별 `mealModes`는 점심/저녁 각각 `auto|required|excluded`다. 기본 auto는 식사 창과 활동 시간의 양의 교집합이 없으면 `outside_activity`, 있으면 `required`다. 사용자가 제외하면 `excluded`를 명시한다. 교집합이 식사시간보다 짧거나 식사+우회가 활동 종료 전 확보되지 않으면 `needs_input`으로 사전 차단하고 조용히 생략하지 않는다. 출력 `mealRequirements`에 계산 결과·사유를 보존한다.
- `REQ-8314`: UI는 최대 7일을 순차적인 하루 요청(`generationScope=day`)으로 실행한다. 각 요청은 90초·경로 100회·생성+수정 2회 이내이며 하루 응답마다 결과/진행률을 표시한다. 실패한 날도 사유를 남기고 다른 날의 결과는 보존한다. 변경/취소 시 이후 요청을 중단한다. 기존 trip 요청 호환은 유지하되 전체 경로 상한을 700회(7×100)로 맞추고 90초 deadline은 유지한다. 하루 요청에서 다른 날짜를 미배정으로 오인하지 않는다. 일일/분당 전역 제한은 그대로 적용하며 하루 HTTP 요청마다 계수한다.
- `REQ-8315`: 모델 형식 오류·필수 누락·시간표 위반이 수정 후 남으면 `generation_failed`다. `infeasible`은 기존 추천에서 확인된 배정 불가능에만 사용한다. 오류를 만든 제안과 여행 조건 전체의 불가능을 구분하며 거절된 시간표는 표시하지 않는다.
- `REQ-8316`: 수정 호출에 실제 조회한 경로의 출발/도착 ID, 출발시각, 초/분 소요시간, 도착예상, 다음 방문시각, 부족 분, 출처/조회시각/경로 참조를 전달한다. 기존 참고 이동표와 구분하며 수정된 시각의 구간은 다시 조회한다.
- `REQ-8317`: 실제 품질 평가는 아래 개발용 합격 기준으로 검사한다. 모의 데이터나 미수집 지표는 통과로 처리하지 않는다. 가격·환율은 하드코딩하지 않고 실행 시 확인한 공급자 가격표와 비용 산정 근거를 평가 기록에 첨부한다.

### 실제 품질 gate — 개발용 후보 기준, 실제 평가는 미수행

공개 장소 20~30곳, 고정 시나리오 최소 10개를 각각 3회 이상 반복한다. 1/3/7일, 오후 도착/오전 출발, 마감/휴무, 식사 충돌, 경로 시각 변경, 선택 장소 과다를 포함한다. 각 시나리오의 실현 가능한 기준 일정은 동일 후보·시간·운영정보·경로 스냅샷으로 별도 검증하고, 원래 카드 순서를 기준으로 가능한 일정과 비교한다. 실패 주입 시나리오는 정상 생성 성공률 분모와 분리해 기대 실패 정확도를 검사한다.

| 지표 | 개발용 합격선 |
|---|---|
| 알려진 필수 제약 위반을 성공 표시 / 근거 위조 / 미확인 표시 누락 | 각각 0건 |
| 실현 가능한 정상 시나리오의 전체 여행 생성 성공률 | 90% 이상; 일부 날짜 실패는 여행 실패 |
| 성공 일정의 필수/anchor 보존 | 100% |
| 추천 점수 가중 장소 보존율 | 동일 시나리오 기준 일정 이상; 장소 축소로 이동시간만 개선한 결과는 불합격 |
| 동일 방문 장소 집합의 총 도로 이동시간 | 기준 일정 대비 평균 비율 1.05 이하; 다른 집합은 별도 보고하고 이동 개선으로 집계하지 않음 |
| 지연 | 일자별 p95 90초 이하; 7일 여행 전체 p95 630초 이하, 전체/일자 지연 모두 기록 |
| 비용 | 완성된 하루 평균 US$0.10 이하, 실패/수정/모든 경로 호출 비용 포함; 미확인 가격은 미검증 |
| 실패 주입/부분 일자/상태 분류 | 기대 결과 일치 100% |

합격선은 평가 전에 고정한다. 변경 시 근거와 버전을 갱신하고 기존 결과를 같은 기준으로 다시 비교한다. 성공률만으로 출시하지 않으며 실제 데이터 coverage·공급자/프록시 검증도 기존 AC에 따라 별도로 필요하다.

평가 기록은 시나리오 ID·반복 번호·정상/실패 주입 구분, 후보 ID와 원래 추천 점수, 필수/anchor, 고정 입력·데이터/모델/프롬프트/정책 버전, 검증된 기준 일정, 생성 결과와 위반/unknown, 하루 및 전체 wall time, 성공/실패 호출의 토큰·경로 횟수와 비용을 연결한다. 이는 공개 장소로 만든 평가 fixture이며 실제 사용자 일정을 저장하지 않는다. 가중 보존율은 배정된 후보의 원래 비음수 추천 점수 합/전체 후보 점수 합으로 계산하고 원래 점수가 모두 0이면 장소 수 비율을 사용한다. 기준 일정이 실현 가능하지 않거나 비교 집합/가격/지표가 없으면 해당 gate는 `not_evaluated`다. p95는 정렬된 표본의 `ceil(0.95×N)`번째 값, 비용은 모든 시도 총비용/완성된 일자 수로 계산하며 분모 0은 실패다. 서버가 응답하기 전 연결이 끊겨 호출 수를 모르면 0으로 집계하지 않는다.

정상 시나리오의 성공은 모든 일차가 `validated|verification_required|partially_scheduled`이며 알려진 위반 없이 필수/anchor를 보존한 경우다. 확인 필요 표시와 데이터 coverage는 별도 gate로 유지한다. 선택 장소가 빠진 부분 일정은 성공률과 별개로 가중 보존율을 충족해야 한다. 가중 보존율은 시나리오별 반복 평균을 기준 일정과 비교하며 동일 장소 집합의 이동 비교 표본이 없으면 이동 gate를 통과시키지 않는다.

## 이번 구현 범위와 결정 — 구현 전 기록 (2026-09-22)

- **승인된 범위**: 실제 시작·종료일 필수, 기존 추천 점수와 `schedule.dayClusters`의 일자 배정 보존, 일자별 LLM 순서·시간 생성, 필수·anchor 보존, 운영정보·자동차 경로·체류·시작/종료 제약 검증, 리뷰 근거 저장·재사용, 식사 연결 계약, 기존 API/평가/리뷰 회귀 및 로컬 모의 검증이다. 식당 검색·랭킹·삽입과 운영 배포는 제외한다.
- **개발 기본값(사용자 확정 서비스 정책 아님)**: GPT-5.6 Terra 후보를 서버 환경설정으로 교체, 카카오모빌리티 자동차, 점심 11:30~14:00·저녁 17:30~20:00 각각 60분, 식당 추가 이동 총 20분, 방문당 별도 여유 10분을 한 번만 적용한다. 식사 창/길이/우회는 UI 수정 가능하다. 비자동차는 명시적 미지원으로 차단한다.
- **입력 계약 결정**: 기존 요청/평가와 분리된 `itinerary-request-v1`, `POST /travel/api/itineraries`; 일자별 공개 장소 ID 시작·종료 선택과 시각이 필수다. `requestId/recommendationRevision/courseVariantId/catalogVersion`을 반영하고 이름·평가 의견·MBTI 원문은 허용 필드에 없다. 추천 입력을 바꾸면 기존 동선을 폐기하며 이전 추천 조건으로 호출하지 않는다.
- **초기 자원 제한 결정**: 최대 7일·하루 6장소, 일자별 생성 1회+조건 수정 최대 1회, 요청 64 KiB, 동시 실행 2건, 단일 요청 총 deadline 90초 및 제한된 방향별 경로 조회. 공개 endpoint는 별도 분당/일일 요청 상한과 feature flag를 사용한다. 서버 프로세스 재시작을 넘는 전역 과금 상한은 공급자 프로젝트 예산으로 별도 설정한다. 숫자는 개발 기본값이며 운영 부하검증 전 확정 정책이 아니다.
- **데이터 결정**: 기존 지도/리뷰/평가 데이터를 덮어쓰지 않고 별도 서버 카탈로그·운영정보·공개 리뷰 분석 산출물을 만든다. 운영 원문·출처·조회시각 및 날짜 예외/중간 휴게/입장 마감/자정 경계를 표현하되 불명확 파싱은 unknown이다. 원천 미수집·오래됨·충돌은 확인 필요로 남긴다. 공식 체류 → 근거 리뷰 → 유형별 임시값 순으로 사용한다.
- **검증 결정**: LLM 출력에는 일정 제안만 허용하고 권위 있는 시간/경로/근거는 서버에서 조합한다. 식사 전후 기본 경로와 우회 허용량을 반환하고 삽입 후 재검증 함수를 둔다. 일몰은 실제 날짜·좌표로 계산한 추정값과 계산 버전을 표시한다. 강제 방문 가능 여부와 리뷰 선호는 분리한다.
- **LLM 연결 결정**: 공통 structured 인터페이스와 테스트 대역을 사용한다. 최신 공식 모델/Structured Outputs 문서를 확인하고 실제 최초 호출 전에 계정의 모델 접근을 확인한다. 환경변수 존재 여부만 확인하며 키를 출력하지 않는다. 공개 리뷰 분석은 별도 사전 생성·캐시로 재사용하고 일정 요청에서 원문 분석을 반복하지 않는다.
- **검증 및 완료 경계**: AC-8301~8312의 모의 테스트·기존 회귀, 실제 공개 장소 20~30곳의 체류·식사·왕복 표본 점검을 수행한다. 실제 모델/경로/운영정보 조회는 키와 외부 접근이 가능할 때만 검증하며, 불가하면 미검증으로 기록하고 SPEC을 In Progress로 유지한다. 초기 로컬 `docs/research/` 변경은 보존한다.

| 장소 추천 | `ccu-mmr.js`의 `rank()`가 브라우저에서 선호 기반 순위·코스 variant를 생성 | 추천 결과와 원래 관련도 유지 |
| 일자 배정 | `buildSchedule()`이 `schedule.dayClusters[]` 생성. 자동차 15km·비자동차 5km 중심 반경, 하루 최대 6곳·대표 유형당 1곳 | 하루에 들어갈 장소 후보로 재사용 |
| 표시 순서 | 일자 `placeIds`는 필수 장소·anchor·추가 추천을 이어 붙인 순서 | 방문 순서나 도착시간으로 해석할 수 없음 |
| 화면 | `app.js`의 `runRecommendation()` → `renderRecommendationOutput()` → `renderSchedule()` | 추천 뒤 별도 비동기 동선 단계 추가 가능 |
| 지도 데이터 | 2,153곳, 그중 41축 추천 준비 1,663곳. 좌표와 대표 유형 포함 | ID 기반 서버용 최소 카탈로그 생성 필요 |
| 카카오 리뷰 | SQLite 4,817건. 추천 준비 장소 중 후기 보유 1,094곳, 본문 보유 1,061곳 | 방문 시간대·체류시간 분석에 재사용 가능하지만 전체 coverage가 아님 |
| 리뷰 시점 | manifest의 수집 시각 `2026-08-23T23:55:05.456101+09:00`, 당시 최대 5건 스냅샷 | 현재 운영시간이나 전체 방문자 의견으로 취급하지 않음 |
| 운영정보 | TourAPI 수집기는 `areaBasedList2` 기본정보를 수집. 지도 번들에는 정규화된 운영시간·휴무·최종 입장시간·체류시간 필드가 없음 | 별도 수집·정규화 필요 |
| 이동정보 | 실제 경로·교통수단별 소요시간 연동 없음. `transportMode`는 `car` 또는 `no_car` | 비자동차를 대중교통·도보·택시 중 하나로 추측하면 안 됨 |
| 서버 | 표준 라이브러리 Python 서비스가 평가 저장과 리뷰 조회 제공. LLM·동선 endpoint 없음 | 기존 배포 구조에서 모듈을 분리해 추가하는 안 |
| 배포 | Vercel 정적 UI가 기존 서버의 평가·리뷰 endpoint로 프록시. 서버 배포 스크립트의 Caddy 경로도 두 API만 명시 | 새 endpoint는 Vercel과 기존 서버 양쪽 경로 추가 필요 |

`result.items`의 Top-N과 `schedule.dayClusters[].places`는 동일 집합이 아니다. 동선 입력은 실제 일자 배정 결과에서 만들고, Top-N만 전달해 일자 장소를 누락하지 않는다.

### 사용자 확정 요구

- 선호에 따른 장소 추천 다음에 동선을 만든다.
- 방문 순서·시간표 작성은 LLM API 호출을 사용한다. 별도 수식 기반 최적화 알고리즘을 만들지 않는다.
- 교통편, 이동시간, 별도 수집한 영업시간, 리뷰에 나타난 낮·일몰·야간 방문 적합성을 고려한다.
- 점심·저녁 시간의 동선 근처에서 후속 식당 검색·추천을 할 수 있어야 한다.
- **동선 생성에는 실제 여행 날짜가 필수다. 날짜 없는 기간 선택에 대한 동선·가상 시간표는 제외한다.**

### 초기 제안과 가정 — 채택 여부는 상단 구현 결정 참조

- 1차는 기존 일자 배정을 유지하고 하루 안의 방문 순서·시간을 생성한다. 일자 간 재배정은 후속 범위로 제안한다.
- 기존 일자 배정의 필수 장소와 anchor를 보존한다. 시간상 넣을 수 없는 선택 장소는 사유와 함께 미배정으로 반환한다.
- 초기 외부 경로는 자동차·카카오모빌리티로 구현했다. 비자동차 제공자는 후속 범위다.
- 공통 LLM 인터페이스를 리뷰 분석과 일정 생성이 함께 사용한다. OpenAI GPT-5.6 Terra는 교체 가능한 개발 후보이며 운영 품질 확정은 아니다.
- SPEC-018의 수식 기반 일자 배정 초안은 선행 구현 조건이 아니며 이번 문서가 그 기능을 구현하거나 대체 완료한 것은 아니다.

- 기존 추천 점수, 유형 상한, 일자 지도 강조와 장소별 평가를 보존한다.

- 맛집 후보 수집·랭킹·실제 식당 삽입 구현. 이번 범위는 연결 계약까지다.
- 전역 최단 경로 보장, 수식 기반 최적화, 기존 추천 점수 변경, SPEC-018 구현.

- 예약·결제, 실시간 날씨에 따른 자동 재계획, 항공·선박 예약 및 복합교통 시간표 최적화.

## 요구사항

- `REQ-8301`: 출발일·종료일이 있는 요청만 동선 생성에 진입한다. 기간 정수만 있는 요청과 날짜 미정 요청은 UI·서버 모두 차단하고 날짜 입력을 안내한다. 날짜 순서·허용 범위를 검증한다.
- `REQ-8302`: 기존 추천 결과에 별도 동선 결과를 연결한다. 원래 점수·variant·일자 후보·제외 조건·필수 장소·anchor·하루 유형 상한을 임의 변경하지 않는다. 시간표 입력과 추천 revision을 연결한다.
- `REQ-8303`: 장소별 운영시간·휴무·입장 마감·예외 운영일을 원문·출처·확인 시각과 함께 보관한다. 불명확·충돌·오래된 정보는 `unknown` 또는 `verification_required`로 처리하며 상시 개방으로 간주하지 않는다.
- `REQ-8304`: 리뷰에서 낮·일몰·야간 적합성과 체류시간 근거를 구조화하고 `review_id`를 연결한다. 리뷰 없음·본문 없음·상충을 처리한다. 리뷰 추론은 운영시간 사실을 덮어쓰지 않는다.
- `REQ-8305`: 실제 이동수단에 맞는 경로 제공자의 예상 이동시간을 사용한다. 출발지·도착지 방향, 조회 시점과 예상 출발 시각을 보존한다. LLM이 이동시간을 생성하거나 직선거리로 확정 이동시간을 대신하지 않는다.
- `REQ-8306`: 일자별 출발·종료 위치와 활동 가능 시간, 체류시간, 이동·대기·휴식 여유를 입력에 포함한다. 누락은 `needs_input` 또는 명시적인 추정 정책으로 처리하며 숙소·항공편을 임의 생성하지 않는다.
- `REQ-8307`: LLM은 허용된 장소 ID에서 방문 순서와 시간 배치를 제안하고, 시간대 선택 이유에 근거 ID를 붙인 구조화 결과를 반환한다. 모델·프롬프트·스키마·카탈로그·운영정보·리뷰·경로 버전을 추적한다.
- `REQ-8308`: 서버가 ID, 중복·누락, 시간 겹침, 이동·체류·식사 시간, 운영시간·입장 마감, 종료 시각을 독립 검증한다. 알려진 필수 제약 위반은 성공으로 반환하지 않으며 필수 장소를 조용히 삭제하지 않는다.
- `REQ-8309`: 점심·저녁의 허용 시간대·소요시간·앞뒤 장소/출발지/종료지·경로 참조·허용 우회시간을 반환한다. 식당 미선정 상태를 표시하고, 후속 식당 확정 시 이동시간과 이후 일정을 재검증해야 한다.
- `REQ-8310`: LLM·경로 호출 실패, 시간 초과, 잘못된 출력, 지원되지 않는 교통수단에서 기존 장소 추천은 유지한다. 수정 요청·재시도·병렬 호출에 상한을 두고 오래된 응답으로 새 결과를 덮어쓰지 않는다.
- `REQ-8311`: API 키는 서버에만 둔다. 리뷰는 비신뢰 데이터로 다루고 외부 LLM에 이름·평가 의견·MBTI 원문을 전송하지 않는다. 공개 장소 데이터 캐시와 사용자 일정 데이터를 분리한다.
- `REQ-8312`: 기존 추천·평가·리뷰 회귀와 동선 고정 시나리오를 검증한다. LLM 출력 자체의 완전한 결정성을 약속하지 않고 검증기·입력·출력·버전 기록으로 재현·비교한다.

## 입력과 출력 — 구현 계약

새 계약은 기존 `schedule` 객체와 분리한 `itinerary-request-v1` / `itinerary-result-v1`이며 endpoint는 `POST /travel/api/itineraries`다. `schemaVersion` 필드를 사용한다.

### 요청

- `requestId`, `recommendationRevision`, `courseVariantId`: 현재 추천과 요청을 연결한다. 브라우저는 `sourceMapVersion`을 전송해 지도 데이터·유형 버전을 비교한다. `catalogVersion`은 선택이며 제공하면 서버 카탈로그 해시와 같아야 한다.
- `travelWindow`: 필수 `{startDate, endDate}`; 유효한 `YYYY-MM-DD`. 날짜는 서버에서도 재검증한다.
- `timezone`: `Asia/Seoul`.
- `routeMode`: 구체적인 이동수단. 기존 랭커의 `car|no_car`와 구분하고 지원 여부를 검증한다.
- `generationScope`: `day|trip`, 생략하면 기존 `trip`. 화면은 `day`로 한 일차씩 전송하되 전체 `travelWindow`와 원래 일차 번호를 보존한다. `day`에서는 `days` 길이가 1이어야 하고 다른 날짜의 미배정 경고를 만들지 않는다.
- `days[]`: `dayIndex`, `date`, `placeIds`, `requiredPlaceIds`, `anchorPlaceId`, `startLocation`, `endLocation`, `startTime`, `endTime`, `mealModes`. 식사 포함 정책은 REQ-8313을 따른다.
- 위치: 우선 공개 장소 ID로 선택하고 서버 카탈로그의 `{lng, lat}`를 사용한다. 좌표 배열을 쓰면 `[경도, 위도]`. 사용자 정확 좌표 입력은 보관·고지 정책 확정 전 추가하지 않는다.
- 시간: 요청의 현지 시각은 `HH:mm`, 내부 비교는 날짜를 포함한 시각, 결과는 `+09:00`이 있는 ISO 8601. 자정 이후 운영은 다음 날로 정규화한다.
- `mealPreferences`: 점심·저녁 각각 허용 시작·종료 시각, 식사 분, 우회 허용 분. 개발 기본값은 상단과 `itinerary_policy.json`에 있으며 UI에서 변경 가능하다. 식사 15~180분, 추가 이동 0~60분을 허용한다.
- `visitPace` 또는 사용자 체류시간 override는 미구현이다. 서버가 공식 정보·리뷰·버전된 유형 기본값 순으로 하한을 정하고 LLM이 마감에 맞추기 위해 체류를 줄이면 차단한다.

브라우저는 원본 리뷰·영업정보·경로시간을 권위 있는 값으로 보내지 않는다. 서버가 ID로 카탈로그·sidecar를 조회하고 클라이언트의 장소 정보·유형·수치 변조를 검증한다. LLM에 전체 MBTI 프로필 대신 일정에 필요한 장소·기존 우선순위·명시적인 여행 속도만 전달한다.

### 장소 시간 정보

- `operatingInfo`: raw text, 주간 운영 구간, 날짜별 예외, 휴무, 입장 마감, `sourceRefs`, `checkedAt`, `status`.
- `visitInsights`: `preferredPeriods[]` (`daylight|sunset|night|any|unknown`), 선택적 체류시간 범위(분), 대기·보행 관련 근거, `evidenceReviewIds`, 상충/부족 상태, 모델·프롬프트 버전, 입력 해시.
- 체류시간은 출처 기반 관람시간 → 리뷰 근거 추정 → 버전된 유형별 기본값 순으로 사용한다는 안이다. 추정·기본값은 사실과 구분하고 값을 정책 파일로 관리한다.
- 일몰·일출은 실제 날짜·좌표에서 별도 계산/조회한다. LLM이 임의로 18시 같은 고정 시각을 지정하지 않는다. NOAA fractional-year 근사 계산을 사용하고 날짜별 계절 회귀를 검사한다. 지형·날씨에 따른 가시성은 검증하지 않는다.

### 응답

- `status`: `validated|verification_required|partially_scheduled|generation_failed|infeasible|needs_input|unavailable`. `generation_failed`는 제한된 모델 시도로 유효한 제안을 얻지 못한 상태, `infeasible`은 기존 추천의 배정 불가능 상태다. `validated`도 입력 시점의 예상 일정이며 실제 이동 보장이 아니다.
- `days[].stops[]`: 장소 ID, 방문 순서, 도착·출발, 체류 분과 근거 종류, 운영정보 확인 상태, 시간대 선택 근거 ID.
- `days[].legs[]`: 출발·도착 위치 ID, 예상 출발·도착, 소요시간, 제공자·조회 시각·예측 기준, 경로 참조. 원천 초 단위를 유지하고 표시 분 변환 시 보수적으로 올림한다.
- `days[].mealSlots[]`: `slotId`, `lunch|dinner`, 허용 시간대와 배정 시간, 식사 소요시간, 앞뒤 위치, 관련 경로 참조, 우회 허용 분, `restaurantStatus=pending`.
- `days[].mealRequirements[]`: 점심/저녁 각각 `mode`, `status=required|outside_activity|excluded`, 원래 창·소요시간·안내 문구. 슬롯이 없는 식사의 이유도 표시한다.
- `days[].unscheduledPlaces[]`: 입력 중 미배정된 모든 장소와 이유, 필수 여부. 시간표에 없어진 장소를 누락하지 않는다.
- `violations[]`, `unknowns[]`, `assumptions[]`, `provenance`: 검증 결과와 데이터 시점·LLM·프롬프트·설정 버전.
- 일정 상태 외에 `restaurantIntegrationStatus=pending`을 유지한다. 식당 선택 전에는 식당까지의 이동 검증이 완료된 것으로 표시하지 않는다.

## 설계 — 초기 구현 순서와 판단 기준

### 1. 연결 계약과 날짜·이동 입력

`rank()`와 `buildSchedule()` 결과는 유지하고 `dayClusters`를 새 요청으로 변환하는 경계를 먼저 만든다. 실제 날짜, 이동수단, 출발·종료 위치/시간을 확인한 뒤 사용자가 동선 만들기를 실행한다. 기간만 선택했으면 실제 날짜 입력으로 유도하고 LLM을 호출하지 않는다.

추천 화면에 있던 날짜 미정/기간 선택을 전부 제거할지는 이번 동선 요구와 별개의 기존 UI 변경이다. 이 초안은 해당 선택만으로는 새 동선을 만들 수 없도록 하는 범위를 확정하며, 날짜 없는 기존 근사 군집을 시간표로 표시하거나 새 동선으로 승격하지 않는다.

완료 기준: 고정 응답으로 요청·응답과 로딩·오류·날짜 누락 상태를 검증할 수 있다.

### 2. 영업정보 수집과 서버 카탈로그

기존 TourAPI ID를 그대로 사용해 별도 상세정보 수집기를 만든다. TourAPI 소개정보를 우선 조사하고 누락은 공식 장소 출처로 보완할 수 있도록 수집 경계를 둔다. 현재 API의 유형별 필드와 실제 응답은 구현 초기에 표본으로 확인한다. 기존 웹 조사 문장이나 카카오 리뷰를 최신 영업시간으로 승격하지 않는다.

원문과 정규화 결과를 날짜별 sidecar·manifest로 저장하고, 서버용 최소 장소 카탈로그와 결합한다. 영업시간·주간 휴무·계절별 시간·입장 마감·자정 경계·공휴일 예외를 각각 표현한다. 설명이 모호하면 원문과 `unknown`을 보존한다. 수집은 재개 가능하게 만들고 실패·누락 coverage를 보고한다.

완료 기준: 대표 유형 표본에서 원문과 구조화 값이 연결되고, 파싱 실패·누락이 방문 가능으로 바뀌지 않는다.

### 3. 공통 LLM 인터페이스와 리뷰 분석

공급자 중립 `generate_structured(task, input, schema, timeout)` 형태의 얇은 인터페이스를 제안한다. 운영 키·모델은 서버 설정에서 주입하고 테스트에서는 가짜 응답을 사용한다. 기능은 구조화 출력, 응답 검증, 시간 제한, 제한된 재시도, 토큰/지연/오류 집계에 한정한다.

카카오 DB의 승인된 ID 연결과 작성자명이 제거된 리뷰를 읽어 장소별 시간대·체류시간을 미리 분석한다. 리뷰 입력 해시·모델·프롬프트 버전이 바뀐 장소만 재분석한다. 방문 시간대 결론마다 리뷰 ID를 검증하고, 관련 없는 리뷰·별점만 있는 리뷰·상충 리뷰는 `unknown`/상충 상태로 남긴다. 리뷰 속 명령문은 실행 지시로 사용하지 않는다.

완료 기준: 매 일정 요청에서 같은 리뷰를 반복 분석하지 않으며 근거 없는 시간대·체류시간을 사실로 저장하지 않는다.

### 4. 이동시간 제공자 연결

경로 제공자를 `route_provider` 뒤로 분리한다. 전체 1,663곳 조합을 계산하지 않고 해당 일자의 최대 6곳과 시작·종료 위치 사이에 필요한 **방향별** 이동시간을 조회한다. 서로 반대 방향의 시간이 같다고 가정하지 않는다.

초기 순서 결정용 시간 표와 최종 선택 경로를 구분한다. LLM이 시간표를 제안하면 실제 배정 출발 시각으로 선택 구간을 다시 조회/검증한다. 캐시 키에 이동수단·좌표·날짜/시간대·제공자 옵션을 넣는다. 미래 시각 예측을 지원하지 않으면 조회 시점 추정이라는 제한을 명시한다. 조회 횟수·재검증 횟수·총 deadline에 상한을 둔다.

완료 기준: 자동차/대중교통/도보를 섞지 않고, 경로 없음·제공자 실패를 0분이나 LLM 추정으로 바꾸지 않는다.

### 5. LLM 시간표 생성과 서버 검증

서버가 일자별 장소, 운영 구간, 리뷰 분석 요약, 체류시간, 이동시간, 시작/종료, 식사 조건을 조합한다. 일자 단위 구조화 호출과 부분 성공 보존을 구현했다. 하루 요청으로 특정 일차를 다시 생성할 수 있지만, 실패한 날만 다시 만드는 화면 동작은 미구현이다.

LLM은 이 입력 안에서 순서·시간·식사 구간을 제안한다. 서버가 날짜/ID/중복/미배정/유형 상한/운영시간/입장 마감/시간 겹침/이동·체류 하한/종료 시각을 검사한다. 알려진 위반은 오류 목록을 붙여 수정 호출 1회까지만 허용한다는 안이다. 그래도 위반하면 성공 일정으로 노출하지 않는다. 데이터가 없는 제약은 검증 통과가 아닌 확인 필요로 남긴다.

수정 후에도 모델의 필수 장소 누락·위반·형식 오류가 있으면 해당 사유와 `generation_failed`를 표시하고 다른 날짜의 유효 결과는 보존한다. 여행 조건 전체가 불가능하다는 증명으로 취급하지 않는다. 기존 일자 배정의 `infeasible`은 그대로 보존한다. 필수 제약 위반 없이 선택 장소만 빠지면 `partially_scheduled`로 표시한다. 오류가 없더라도 미확인 운영정보가 있으면 `verification_required`다. 복수 상태 원인은 `violations`·`unknowns`에 모두 남긴다.

완료 기준: 빠른 마감·일몰 선호·긴 이동·점심 시간 충돌 사례에서 사실 기반 결과 또는 정직한 미배정/실패 사유를 반환한다.

### 6. 시간표·지도 표시와 식당 연결 계약

`app.js`에 동선 전용 상태와 `itinerary.js` 클라이언트를 추가하는 안이다. 추천 목록을 먼저 표시하고 명시적 동선 생성으로 호출한다. UI는 순번, 도착/출발, 이동·체류시간, 점심·저녁 자리, 근거 요약과 확인 필요를 보여준다. 경로 도형은 제공자가 반환한 경로일 때만 실제 이동 경로로 표시한다.

중요한 기존 코드 경계: `renderRecommendationOutput()`은 평가 세션을 새로 만들므로 동선 응답을 그 함수로 다시 렌더링하지 않는다. 동선 전용 갱신에서 현재 평가와 이름·별칭·선택 장소를 보존한다. 추천 재실행·variant·날짜 변경은 동선을 무효화하고 요청을 중단하며 revision이 다른 늦은 응답을 무시한다.

식당 검색은 식사 slot의 시간대와 앞뒤 위치·경로를 입력으로 삼는다. 단순 위경도 중점 하나로 검색 위치를 확정하지 않는다. 식당 선택 후에는 A→식당→B 이동, 식당 영업·주문 마감, 체류시간을 다시 반영해야 한다는 후속 계약을 둔다. 첫/마지막 식사는 시작·종료 위치도 앞뒤 지점으로 사용할 수 있다. 식사 자리를 못 만들면 조용히 생략하지 않고 사유를 반환한다.

완료 기준: 기존 모바일/데스크톱 추천·지도 강조·평가 자동 저장을 유지하면서 식당이 아직 미선정인 날짜별 시간표를 표시한다.

### 7. 통합 검증과 배포 준비

고정 시나리오와 기존 회귀를 먼저 통과시킨 뒤 대표 제주 장소로 제한된 실제 API 평가를 한다. 서버의 새 모듈·설정·카탈로그를 Docker 이미지에 넣고 Caddy의 명시 경로와 Vercel의 동일 출처 프록시에 동선 endpoint를 추가한다. 기존 프록시의 Origin 처리를 그대로 넓히지 말고 새 경로에 맞춰 검증한다.

LLM 비용이 발생하는 공개 endpoint에는 요청 크기·일수·호출 빈도·동시 실행·토큰·총 비용 상한을 둔다. 운영 타임아웃을 초과하면 실패시키고 추천 결과를 보존한다. 초기에는 bounded synchronous 요청을 제안하며, 표본 지연시간이 프록시 제한에 맞지 않으면 job/poll 방식으로 SPEC을 먼저 변경한다.

완료 기준: 새 기능을 끈 상태에서도 기존 서비스가 동작하고 실패 시 동선 기능만 되돌릴 수 있다.

### 첫 버전 개발 기본값 — 사용자 확정 운영 정책 아님

## 예외와 폴백

- 날짜 없음: 생성 차단, 날짜 요청. 임의 날짜·요일을 채우지 않는다.
- 출발/종료 또는 이동수단 불명: 필요한 입력을 반환하고 LLM 호출 전 중단한다.
- 기존 `schedule.status=infeasible`, 빈 일자: 원래 사유를 유지하고 시간표로 해결한 것처럼 표시하지 않는다.
- 리뷰 없음/근거 불충분: 시간대 `unknown`; 체류시간 기본값을 사용하면 추정으로 표시한다.
- 운영정보 불명·오래됨·충돌: `verification_required`; 높은 선호나 좋은 리뷰로 통과시키지 않는다.
- 경로 없음·교통수단 미지원: 해당 구간을 방문 가능한 이동으로 만들지 않는다. API 장애는 `unavailable`과 재시도 안내다.
- LLM 거절/형식 오류/존재하지 않는 ID/근거 위조: 검증 실패. 제한된 재시도 후 기존 추천을 유지한다.
- 입장 마감과 일몰 선호 충돌: 입장 마감 우선. 일몰 방문이 불가능하다는 근거를 보여준다.
- 선택 장소 과다: 선택 장소 미배정과 이유를 모두 표시한다. 필수 장소를 제거해 성공으로 만들지 않는다.
- 식당 미선정: 식사 시간·우회 여유만 확보한 상태임을 표시하고 식당 확정 뒤 재검증한다.

- 데이터 마이그레이션: 기존 지도 번들·카카오 리뷰 DB·사용자 평가 DB를 덮어쓰지 않고 신규 공개 장소 sidecar/카탈로그로 시작한다.
- 호환성 영향: 원래 `schedule`은 근사 일자 배정으로 유지하고 새 `itinerary`를 별도 보관한다. 동선 변경만으로 평가 세션을 초기화하지 않는다. 기존 자동 평가 payload에는 새 출발·종료 위치나 LLM 원문이 자동 포함되지 않도록 명시적인 필드 선택을 사용한다.
- 보안·개인정보: 공용 장소 ID·좌표, 날짜·활동 시간과 최소 일정 조건만 처리한다. 리뷰 본문은 공개 후기 분석에만 보내고 사용자 이름·의견·MBTI 원문은 보내지 않는다. 본문 안 개인정보는 외부 전송 전에 최소화한다.
- 저장 구현: 공개 장소 분석은 버전된 sidecar로 보관하고 원본 해시로 갱신/철회한다. 사용자 일정·장소 선택·원문 프롬프트는 초기 버전에서 서버에 영속 저장하지 않는다. 요청 처리 후 해제하고 클라이언트는 현재 탭 메모리에서 초기화/종료 시 삭제한다. 운영 로그에는 정해진 API 경로·비식별 상태만 남긴다. 호출 횟수와 버전은 응답 provenance로 반환한다. OpenAI는 `store=false`로 호출하며 공급자 보관 설정은 실운영 전에 확인해야 한다.
- 기존 기준 문서와의 차이: 리뷰 표시와 별도 시간대 추론 경계, 날짜·공개 위치의 외부 전송 목적을 기준 문서와 사용자 고지에 반영했다. 키가 없어 실제 분석은 아직 실행하지 않았다.

## 테스트 계획

### 여기서 말하는 검증

1. **자동 조건 검사**: LLM 시간표가 입력으로 제공한 운영시간·이동시간·체류시간·필수 장소 조건을 지키는지 코드로 확인한다. 예를 들어 17시 마감, 관람 60분, 다음 장소까지 이동 30분인 가상 조건에서 `16:30~17:30 관람 → 17:40 다음 장소 도착`은 마감 위반과 이동시간 부족으로 검출해야 한다. 위반 목록을 LLM에 전달해 제한된 횟수 안에서 수정한다.

## 구현 결과

**로컬 기능·모의 검증 구현, 실제 API 검증 대기**다. 전체 완료가 아니므로 상태는 `In Progress`를 유지한다.

- `itinerary_service.py`·`itinerary_validation.py`: 실제 날짜/공개 ID/유형 검증, 방향별 참고 경로와 실제 배정 출발 시각 재조회, 날짜별 structured 생성과 최대 1회 수정, 운영정보·체류·필수/anchor·중복·식사·종료 검사. 거절한 시간표는 방문/이동/식사 출력에서 제거하고 해당 일자의 모든 장소에 미배정 사유를 남긴다. 다른 날짜의 유효 결과는 보존한다.
- `llm_client.py`는 리뷰와 일정의 공통 인터페이스다. 서버 모델 설정, 최초 계정 모델 접근 확인, JSON schema/거절/timeout/토큰 제한, `store=false`, 원문 없는 오류를 구현했다. `route_provider.py`는 카카오 자동차 미래 시각 경로의 초 단위를 보존하고 분은 올림한다. 과거 시각·비자동차를 현재 자동차 경로로 대체하지 않는다.
- 운영정보 수집기·정규화기, 공개 카탈로그 생성기, 리뷰 사전 분석/해시 캐시/철회를 구현했다. 원본 DB와 지도 번들은 변경하지 않았다. 카탈로그 빌드는 리뷰 근거와 승인된 장소 관계를 원본 읽기 전용 DB에 대조한다. 시작 시 분석 sidecar와 카탈로그 버전이 어긋나면 동선만 비활성화한다.
- 화면·HTTP·Docker·Vercel·Caddy 연결을 구현했다. 동선 응답은 기존 추천 객체와 평가 세션을 다시 생성하지 않는다. 날짜·추천·동선 옵션 변경과 응답 역전을 차단한다. 기존 지도 강조는 유지하며 실제 경로의 새 지도 선 표시는 구현하지 않았다.

### 실제 공개 장소 24곳 표본 — 모의 시간·경로

`python3 scripts/evaluate_itineraries.py --output /tmp/spec083-sample-audit.json`은 실제 랭커가 만든 2026-10-01~04의 4일·24개 `dayClusters` 후보를 사용한다. 기존 순서 중 16곳을 모의 배정하고 선택 8곳은 사유를 남긴다. 점심 12:50~13:50, 저녁 19:00~20:00와 식사당 20분 우회 여유, 방문당 10분을 검사해 알려진 조건 위반 0건이다. 10분 이동은 테스트 대역이며 실제 이동 사실이 아니다.

- 올레 3개 코스와 야영장 2곳, 총 5곳은 체류시간을 확인해야 한다. 일반 기본값으로 확정하지 않는다. 나머지 45/90/120분도 `provisional_type_default`다.
- 1일차(중문)와 3일차(성산)의 기존 표시 순서는 같은 출발/종료 4점의 직선거리 참고 순서보다 각각 1.49배·1.38배였다. 왕복 검토 대상으로 기록했으며 실제 LLM/도로가 개선됐다는 증거는 아니다. 프롬프트는 시작/종료와 방향별 이동표를 사용해 불필요한 왕복을 줄이도록 안내한다.
- 운영정보가 없는 곳은 전부 확인 필요가 남는다. 배·회차·긴 걷기·등산은 자동차와 임시 체류만으로 실행 가능함을 보장하지 않는다.

## 설계와 달라진 점

- 개발 기본값은 버전된 `itinerary_policy.json`으로 구현했고 운영 확정 정책으로 기록하지 않았다. 2026-09-24 v2는 최대 7일, 하루 6곳, 경로 일자당 100회·전체 700회, HTTP 요청당 90초 deadline이다. 화면은 하루씩 순차 요청한다.
- 운영정보 신선도는 개발용 30일이며 여행일과 현재 시각을 모두 고려한다. 출처별 운영 정책과 실제 coverage 평가는 남아 있다.
- 리뷰 분석은 일정 요청 시 호출하지 않고 명시적인 사전 생성으로 저장한다. 키 없는 현재 산출물은 분석 준비용 unknown이며 시간대 결론을 만들지 않았다.
- 식당 우회 허용 20분은 나중 삽입 때 기존 방문 시간을 지키기 위한 추가 여유로 한 번 예약한다. 방문당 10분과 구분한다. 실제 식당 후보 조회/삽입/영업·주문 마감 검사는 후속 범위다.
- 입력 UI는 같은 날짜 안의 시작·종료 시각을 받는다. 서버 검증기는 자정 이후 운영/시각도 검증하고 방문이 걸치는 모든 날짜의 예외 휴무를 확인한다.
- 사용자 체류 override, 새 경로 지도 선, job/poll 방식, 실제 모델 반복 품질/비용 평가기는 미구현이다. `evaluate_itineraries.py`는 실제 장소를 사용하는 오프라인 진단이다.

## 남은 설정과 알려진 제한

1. `OPENAI_API_KEY`, `KAKAO_MOBILITY_API_KEY`, 수집용 `KTO_TOUR_API_KEY`가 이 작업 환경에 없다. 서버 모델 기본값은 `gpt-5.6-terra`, 기능 기본값은 `ITINERARY_ENABLED=0`이다. [서버 실행 안내](../server/travel-feedback/README.md#날짜-기반-동선-spec-083)에 수집·분석·재생성·설정 순서를 기록했다.
2. 새 카탈로그 2,153곳(추천 준비 1,663곳)의 **실제 운영정보 수집 0건**. 원문이 복잡한 계절·휴일·회차 조건은 unknown으로 남기고 근거 있는 정규화가 필요하다.
3. 공개 후기 연결 1,094곳 중 시간 근거 후보 270곳, 시간 근거 없는 824곳. **실제 LLM 리뷰 분석 0건**이며 모두 unknown이다. 리뷰 시점은 2026-08-23 스냅샷이고 현재 사실로 승격하지 않는다.
4. 계정 모델 사용 가능 여부는 런타임 검사 코드와 모의 테스트만 확인했다. 실제 키·프로젝트 권한·예산·데이터 이용/보관 조건을 확인하고 미래 실제 날짜 표본으로 API 검증해야 한다.
5. 화면은 하루씩 요청해 다일의 90초 예산 공유를 피한다. 기존 trip API를 직접 쓰면 7일 경로 호출 상한은 맞지만 전체 90초 deadline으로 일부 날짜가 unavailable일 수 있다. 하루 안에서도 최대 56회 참고 경로를 순차 조회하므로 실제 지연이 크면 deadline을 넘을 수 있으며 실제 프록시·지연·비용 검증은 남아 있다. 7일 화면 실행은 HTTP 요청 7건으로 전역 분당/일일 제한에 계수한다. 특정 선택 장소의 경로 실패는 해당 날짜 전체 unavailable이다. 브라우저 취소는 후속 날짜와 화면 덮어쓰기를 막지만 이미 진행 중인 서버 호출의 비용 취소를 보장하지 않는다. 실패한 날짜만 다시 실행하는 화면은 후속 범위며 현재 생성 버튼은 전체 날짜를 다시 요청한다.
6. 일자 간 재배정, 대중교통·도보·택시, 항공/배 예약·회차, 식당 추천은 지원하지 않는다. 운영정보·교통 데이터의 현실 정확도, 좋은 동선이나 전역 최적해를 보장하지 않는다. 관련 없는 `docs/research/` 로컬 변경은 보존했다.

## 외부 인터페이스 조사 근거

2026-09-21의 초기 조사와 2026-09-22의 구현 시 공식 문서 확인을 구분한다. 공급자는 개발 기본값으로 채택했으며 실제 계정 접근은 미검증이다.

- [한국관광공사 국문 관광정보 서비스](https://www.data.go.kr/data/15101578/openapi.do): 소개정보를 포함하는 관광정보 API다. 유형별 운영시간 필드·파싱 규칙은 실제 명세/표본 확인 후 확정한다.
- [카카오모빌리티 자동차 길찾기](https://developers.kakaomobility.com/guide/navi-api/directions): 방향이 있는 출발지·목적지와 경로별 거리·소요시간을 제공하는 자동차 경로 후보. 소요시간 단위는 초다.
- [카카오모빌리티 미래 운행 정보 길찾기](https://developers.kakaomobility.com/guide/navi-api/future): 미래 출발 시각을 입력받는 경로 후보. 대중교통·도보 지원으로 확대 해석하지 않는다.

2026-09-22 최신 공식 문서 추가 확인:

- [OpenAI GPT-5.6 Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra): 성능과 비용의 균형을 목표로 하는 모델로 안내된다. Responses와 Structured Outputs 지원을 확인했다. 첫 호출 전 `GET /v1/models/{model}`로 계정 접근을 확인하도록 구현했고 실제 계정·일정 품질은 아직 검증하지 않았다.
- [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs): 지정한 스키마에 맞는 구조화 출력 기능. 시간표의 현실성·영업시간 준수는 별도 애플리케이션 검증 대상이다.

- [NOAA 일출·일몰 계산식](https://gml.noaa.gov/grad/solcalc/solareqns.PDF): 실제 날짜·경도/위도 기반 천문 근사 계산의 출처. 날씨·가시성·입장 가능성을 뜻하지 않는다.
