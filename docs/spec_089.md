## 배경

제출 Spec은 사업 전체의 B2B·B2G 방향을 밝히면서도 고객·판매상품·실행 계획을 숙박업체 실증에 과도하게 집중했다. 단가·표본·기간 등 작성 과정의 임의 가정이 본문 핵심 전략처럼 강조되어 있다. 사용자는 산출물 1의 비즈니스 캔버스 평가와 산출물 2의 프로세스만을 작업 범위로 정정하고, 제시한 여섯 수정 항목의 실행을 승인했다.

## 목표

- 고객군별 사용자·구매자·구매 이유와 판매상품·과금 단위를 명확히 한다.
- 기존 자료에서 확인한 문제 근거와 해석·미검증 가설을 구분한다.
- 입력에서 선택까지 구체적인 솔루션 사례를 제공한다.
- 임의 가정을 별도 보완 문서에 모으고 제출본을 사업 전략 중심으로 정리한다.
- Spec과 L1/L2 도면 및 안내·평가 대조 메모의 범위를 동기화한다.

## 비목표

- 프로토타입·별도 논리 모델·활동보고서 제작이나 이를 이번 작업의 부족 사항으로 요구하기.
- 제품 코드·배포·실제 지역 지원 변경, 실제 영업·계약, 시장성·가격 조사 결과 창작.
- 개인별 원문 피드백·정확한 여행 조건·식별 정보를 제출물에 복제하기.

## 요구사항

- REQ-001: 사용자·구매자·상품·도입 접점·측정 가치·과금 단위를 고객군별로 연결한다. 실제 판매 여부와 설계를 구분한다.
- REQ-002: 제주는 현재 MVP 범위로 유지한다. 첫 실증 고객은 선정 조건을 제시하고 숙박 채널은 검증 가능한 진입안 중 하나로 분리한다.
- REQ-003: 기존 익명 피드백을 필요한 범위에서 읽고 집계·비식별 주제만 문제 근거에 사용한다. 코드 자산을 고객 문제나 수익성의 증거로 대체하지 않는다.
- REQ-004: 구체적인 입력→필수 조건→선호 매칭→후보 비교 사례를 설계 예시로 제시하고 사실 미확인·근사 일정 한계를 표시한다.
- REQ-005: 실증비 100만원·2곳·160시간 등 임의 수치를 본문 핵심 전략에서 빼고 선택적 실험 가정으로 분리한다. 확정 일정·가격·성과로 오인하지 않게 한다.
- REQ-006: 평가 대조는 비즈니스 캔버스 6문항과 프로세스 3문항만 다룬다. 제출 안내와 Spec에서 다른 산출물의 추가 작성 요구를 제거한다.
- REQ-007: L1은 사업의 기업·공공 구매자와 여행자·운영·원천 제공자 간 공통 흐름을, L2는 제주 MVP 여행자 흐름과 숙박 실증 예시를 구분한다. Actor별 비기능 책임과 요구사항 연결을 명시한다.

## 입력과 출력

- 입력: 기존 제출본, 사업 제안, SPEC-070과 해당 익명 리포트·집계, 사용자 평가표의 `평가표!A2:D3`.
- 출력: `kaist_app/제출용/`의 Spec v1.2, draw.io·PDF, 동기화한 사업전략 보완·제출 안내·대조 메모.
- 기준일: 2026-09-29. 새 시장 통계·가격 조사는 범위에 포함하지 않는다.

## 설계

본문의 구조와 기존 ID는 최대한 보존한다. §3은 고객·역할, §4는 판매상품·채널·수익구조, §9~10은 성과 중심 검증·단계별 진입으로 수정한다. L1의 기존 연결 구조를 공통 사업 흐름으로 일반화하고 L2-B를 숙박 실증 예시로 남긴다. 계약 단가·지역·파트너·예산은 미결정으로 유지한다.

## 설계와 달라진 점

L1의 기존 17개 연결을 유지하면서 계약상 검수 미통과의 보완·재검수 연결 1개를 추가했다. 일반화한 구매 주체의 실제 결과 검토와 예외를 표현하기 위해 필요했다. 전체 페이지 수와 L2 구조는 유지했다.

## 알려진 제한

기존 베타 피드백은 추천 화면에 대한 반응이며 구매 의사·실제 방문·전국 시장성의 근거가 아니다. 추천 API·고객별 상품화·공공 운영은 미구현 계획을 포함한다. 이번 작업은 문서·프로세스 설계 보완이며 실제 영업·가격 검증·제품 기능 구현을 수행하지 않았다. draw.io 수동 편집 시 PDF를 별도로 갱신해야 한다.
